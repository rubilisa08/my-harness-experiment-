  1. 로컬 PC 내장 GPU(Intel Iris Xe): 압축 도중 매번 드라이버가 타임아웃(TDR)으로 죽음 (`DXGI_ERROR_DEVICE_HUNG`)
  2. 로컬 PC + 소프트웨어 Vulkan(CPU로 GPU 흉내): 에러는 안 나지만 진행이 멈춘 채 30분 넘게 응답 없음
  3. Colab T4 GPU: 3DGS 학습(CUDA 경로)은 문제없었지만, `.sog`가 쓰는 Vulkan(그래픽 경로)은 컨테이너에 드라이버가 아예 없어 실패, 소프트웨어 Vulkan을 설치해도 로컬과 같은 증상(멈춤)이 재현됨
  
  즉 GPU 자체가 아니라 이 변환 도구가 요구하는 Vulkan 그래픽 드라이버가 세 환경 모두에서 정상 동작하지 않아서 막힌 것으로 판단했습니다. 같은 알갱이 개수를 가진 `.compressed.ply`(9.0MB, `.ply` 대비 75% 감소)로 대체 배포했습니다.

function getCount(file) {
  const out = run([file, '--info', 'json', 'null']);
  const info = JSON.parse(out);

  const guess =
    info.numGaussians ??

}

  { label: '.ply', file: input, isSource: true },
  { label: '.compressed.ply', file: input.replace(/\.ply$/, '.compressed.ply') },
  { label: '.sog', file: input.replace(/\.ply$/, '.sog') },
  { label: '.spz', file: input.replace(/\.ply$/, '.spz') },
];

const rows = [];

for (const t of targets) {
  let elapsedMs = null;
  const alreadyExists = !t.isSource && existsSync(t.file) && statSync(t.file).size > 0;
  if (!t.isSource && !alreadyExists) {
    const start = Date.now();
    run(['-w', input, t.file]);
    elapsedMs = Date.now() - start;
  }
  const size = statSync(t.file).size;
  let count = null;
  try {
    count = getCount(t.file);
  } catch (e) {
    console.error(`[경고] ${t.file} 알갱이 개수 조회 실패: ${e.message}`);
  }
  rows.push({
    format: t.label,
    file: basename(t.file),
    sizeBytes: size,
    seconds: elapsedMs == null ? null : (elapsedMs / 1000).toFixed(2),
    count,
    bytesPerSplat: count ? (size / count).toFixed(2) : null,
  });
}

console.log('\n| 형식 | 파일 | 크기(바이트) | 변환 시간(초) | 알갱이 개수 | 알갱이당 바이트 |');
console.log('|---|---|---|---|---|---|');
for (const r of rows) {
  console.log(
    `| ${r.format} | ${r.file} | ${r.sizeBytes.toLocaleString()} | ${r.seconds ?? '-'} | ${r.count ?? '?'} | ${r.bytesPerSplat ?? '?'} |`
  );
}

const counts = rows.map((r) => r.count).filter((c) => c != null);
const allSame = counts.every((c) => c === counts[0]);
console.log('\n' + (allSame
  ? '✅ 네 파일의 알갱이 개수가 모두 같습니다.'
  : '⚠️ 알갱이 개수가 형식마다 다릅니다 — 솎아 낸(decimate) 파일과 바뀐 것은 아닌지 확인하세요.'));

# 내 업무의 적용 지점 도출

> 대상 업무: 경영기획팀/IR팀의 실적발표(컨퍼런스콜) 관련 업무 (`PROBLEM_DEFINITION.md`와 동일한 도메인)

## 1. 후보 목록 (3개 이상)

| 적은 것 | 업무 유형 | 지금 처리 방식 | 병목 | 하루·주당 발생량 | 틀렸을 때 |
|---|---|---|---|---|---|
| **A. 실적발표 음성 → 리스크 브리핑** (지금 구축한 것) | 전사 | 담당자가 컨퍼런스콜 녹음(30~60분)을 처음부터 끝까지 들으며 핵심 리스크를 수기로 메모 | 청취 속도가 실시간 재생에 묶여 있고, 특정 발언을 나중에 다시 찾기 어려움 | **분기당 1회** (주당 환산 시 약 0.08건 — 낮음) | 내부 보고서 초안 단계, 최종적으로 담당자가 검수 후 사용 → 되돌릴 수 있음. 다만 리스크를 놓쳤을 때 "놓쳤다는 사실 자체"를 알아채기 어려움 |
| B. 공시자료·실적보고서 수치 정합성 검사 | 검색·검사 | 보고서 작성 후 사람이 재무제표 표와 본문 서술을 대조하며 검토 | 숫자가 많은 표와 긴 텍스트를 대조하는 단순반복 작업 — 피로가 쌓이면 놓침 | 분기 보고서 + 수시 공시 포함 시 **주당 여러 건** | **공시 이후에는 되돌리기 어려움** — 오류가 그대로 투자자/금감원에 노출되고 정정공시가 필요함 |
| C. 투자자·애널리스트 문의 메일 분류/초안 작성 | 배분·입력 | IR 담당자가 메일을 열어 카테고리(재무/사업/ESG/지분 등)를 파악하고 담당자에게 전달하거나 직접 답변 초안 작성 | 실적발표 직후 1~2주간 문의가 몰려, 반복적인 분류·정형 답변 작성에 시간 소요 | 실적발표 시즌 **하루 5~15건** | 초안 단계이며 사람이 최종 확인 후 발송 → 되돌릴 수 있음 |

## 2. 네 가지 기준으로 판단

| 기준 | A (실적발표 음성) | B (공시 검사) | C (문의 메일 분류) |
|---|---|---|---|
| 판정 기준이 이미 정해져 있다 | ✅ 부채비율>200%, 유동비율<100% 등 명확한 임계값 | ✅ 표 숫자와 본문 서술 일치 여부는 이진 판정 | △ 카테고리 분류는 명확, 답변 "품질"은 주관적 |
| 지난 판정 기록으로 채점 자료를 만들 수 있다 | △ 과거 녹취록+당시 리스크 메모가 있어야 하는데 비정형으로 흩어져 있을 가능성 | ✅ 과거 정정공시 이력이 좋은 채점 자료 | ✅ 과거 메일·답변 이력 (제약: 개인정보 마스킹 필요) |
| 틀렸을 때 되돌릴 수 있다 | ✅ 내부 초안, 최종 검수 있음 | ❌ 외부(투자자)에 직접 노출, 정정 필요 | ✅ 발송 전 사람이 확인 |
| 발생량이 충분해서 개선 효과가 보인다 | ❌ 분기당 1회로 낮음 | ✅ 주당 여러 건 | ✅ 시즌 중 하루 여러 건 |

**결론**: B는 "틀렸을 때" 기준에서 명확히 탈락합니다 — 잘못된 판정이 투자자에게 그대로 나가는 지점이라 이번 PoC 대상에서 제외합니다(템플릿 규칙: "잘못된 판정이 고객에게 그대로 나가거나 사람에게 영향을 주는 지점은 PoC 대상에서 뒤로 미룬다"). A와 C는 각각 4개 중 3개를 만족합니다.

**선택: A (실적발표 음성 → 리스크 브리핑)를 유지**합니다. 네 기준을 전부 만족하는 후보가 없으므로("발생량"에서 A가 약함), 템플릿 규칙대로 가장 많이 만족하는 지점을 고르되 약한 항목을 제약으로 남깁니다.

- **제약**: 이벤트 발생 빈도(분기당 1회)가 낮아, "개선 효과가 반복적으로 눈에 보이는" 유형의 PoC는 아닙니다. 다만 이벤트 1건당 처리 시간(30~60분)이 크고, 실제로 만들어 실행해본 결과(`VALIDATION_RESULTS.md`) 처리 시간 절감·정확도가 실측으로 확인되어, 이미 검증된 자산이 있다는 점을 근거로 유지를 선택했습니다.
- **참고**: C(문의 메일 분류)는 네 기준을 A보다 고르게 만족하는 강한 대안입니다. 발생량 문제를 근본적으로 해결하고 싶다면 다음 PoC 후보로 C를 검토할 가치가 있습니다.

## 3. 성공 기준 (정량, 한 줄)

> **실적발표 녹음 1건당, 핵심 재무 리스크(부채비율/유동비율 등 사전 정의된 임계값 기준) 추출까지 걸리는 시간을 사람의 수작업 대비 50% 이상 단축하고, 사람이 실제로 확인했던 핵심 리스크를 100% 재현한다.**

**정직한 한계**: 위 "사람의 수작업 시간" 기준은 템플릿이 권장하는 "실제로 담당자에게 20건을 처리하게 해서 잰 시간"이 아니라, `PROBLEM_DEFINITION.md`에 적은 가정(녹음 길이의 1.5~2배)을 그대로 쓴 것입니다. 이 프로젝트를 실제 조직에 적용한다면, 이 성공 기준을 확정하기 전에 **담당자가 과거 컨퍼런스콜 녹음 20건을 실제로 청취·메모하는 데 걸린 시간과 오류 수를 먼저 재는 작업**이 선행되어야 합니다. (현재 PoC는 이 실측 기준선 없이, 가정치로 절감률을 계산했다는 것이 한계입니다 — `VALIDATION_RESULTS.md`에서도 "1.75배 가정"이라고 명시하고 있습니다.)

2번과 4번은 2026-09-26에 실제로 수정하고 재실행해 확인했습니다. 같은 날, 다른 두 PoC 예시(사진 검색기·스쿼트 보조도구)를 검토하다가 "모델이 이미 내주는 신뢰도를 계산에 안 쓰면, 모델이 '모른다'고 말한 것을 읽지 않은 셈"이라는 지적이 우리 3번 항목과 정확히 겹친다는 것을 발견해 3번도 같은 날 수정했습니다. 5번(근거 구간만 재생)은 2026-09-27에 구현했고, **그 과정에서 근거 타임스탬프 자체가 잘못된 발언을 가리키던 진짜 버그를 발견해 함께 고쳤습니다**(`VALIDATION_RESULTS.md` 0-1번 섹션 참고). 이제 5개 중 4개(2·3·4·5번)가 충족됐고, **1번(자료 외부 전송)만** 실전 적용 시 남은 과제로 남아 있습니다 — Claude 실제 API 호출 시 세그먼트 텍스트가 외부로 전송되는 것은 로컬 STT만으로는 해결되지 않는 구조적 제약입니다.

| PoC의 산출물 | 작동하는 물건이 아니라 판단이다 — 기준을 못 넘은 이유도 결과다 | "발생량이 낮다"는 기준 미달도 결과로 남겼지, 숨기지 않았다 |

# 문제 정의서 — 실적발표 음성 브리핑 PoC

## 도메인 설명

상장기업 경영기획팀/IR팀의 **실적발표(컨퍼런스콜, 어닝콜) 분석 업무**입니다. 상장사는 분기마다 실적발표회를 열어 경영진이 실적과 전망을 설명하고 애널리스트 질의응답(Q&A)을 진행합니다. 경영기획팀/IR팀 실무자는 이 발표 내용을 듣고 핵심 이슈를 정리해 내부 보고서로 만드는 일을 정기적으로 수행합니다.

이 프로젝트는 [AI Business Briefing & Intelligence Publisher](https://github.com/rubilisa08/AI-project_MVP)의 자연스러운 확장입니다. 그 프로젝트는 PDF·Excel·뉴스 URL 등 **이미 텍스트로 존재하는 자료**만 다뤘지만, 실제 기업 커뮤니케이션의 상당 부분(실적발표, 컨퍼런스콜, 내부 회의)은 **음성**으로 존재합니다.

## 현재의 문제

- 실적발표 녹음(보통 30분~1시간)을 실무자가 처음부터 끝까지 들으며 메모해 핵심 리스크를 추려야 합니다 — 청취 + 정리 시간을 합치면 녹음 길이의 1.5~2배가 소요되는 경우가 많습니다.
- 사람이 들으면서 메모하면 특정 발언(특히 숫자)을 놓치기 쉽고, 나중에 "그 발언이 정확히 몇 분 몇 초에 나왔는지" 다시 찾기 어렵습니다.
- 기존 AI Business Briefing 파이프라인은 PDF/Excel/뉴스 URL만 입력으로 받아, 음성 자료는 분석 대상에서 아예 빠져 있습니다.

## 개선 가설

실적발표 녹음을 **STT(Whisper)로 텍스트화**한 뒤, 기존 프로젝트와 동일한 "원문 인용 기반 리스크 추출 + 팩트체크" 로직에 그대로 태우면,

1. 녹음을 처음부터 끝까지 듣지 않아도 핵심 리스크/이슈를 몇 분 안에 파악할 수 있고,
2. 모든 주장에 "발언 시점(타임스탬프)"이 근거로 자동으로 붙어 나중에 검증이 쉬워집니다.

## 대상 사용자

실적발표 녹음을 정기적으로 청취·요약해야 하는 경영기획팀/IR팀 실무자, 애널리스트.

## 성공 기준

**정량**
- (녹음 길이 기반 수작업 청취+메모 예상 소요시간) vs (STT 처리 시간 + 분석 처리 시간) 비교
- STT 결과와 원본 대본(ground truth)의 일치율 — 이번 PoC는 TTS로 생성한 음성을 사용하므로 원문 대본과 1:1 비교가 가능함(문자 단위 일치율 측정)

**정성**
- STT 텍스트에서 추출된 리스크/이슈가 원본 대본의 실제 내용과 부합하는지
- 각 리스크에 붙은 타임스탬프 근거가 실제 해당 발언 위치와 맞는지
- 기존 AI-project_MVP가 동일한 재무 수치(Excel)로 찾아냈던 리스크(단기 유동성 부족, 높은 부채비율)를 음성 경로로도 동일하게 찾아내는지 — 파이프라인 간 일관성 확인

3. **개선 효과 검증**:

   - 정성: 기존 프로젝트가 Excel 경로로 찾아낸 리스크를 음성 경로로도 동일하게 찾아내는지, 그리고 재무 프로필이 다른 시나리오에서 오탐 없이 동작하는지(9번 섹션)
4. **확장 기능** (10~12번 섹션): 리스크별 근거 오디오 재생(Human-in-the-loop 검증), 발표/Q&A 구간 분리, 음성-재무제표 수치 십자 검증 — 세 가지 모두 실제로 구현하고 실행 결과로 검증했습니다.

## 정확도·보안을 위해 넣은 코드 레벨 가드

- **Grounding 검증**: 리스크의 근거 타임스탬프가 실제 세그먼트와 일치하는지 코드로 재검증 (할루시네이션 가드). 근거 매칭 자체도 느슨한 키워드가 아니라 실제 매칭된 수치 기준으로 정밀화 — 이 정밀화를 통해 "부채총계"를 "부채비율"의 근거로 잘못 잡던 실제 버그를 발견해 고쳤습니다
- **스키마 검증**: 필수 필드/허용값 누락 시 즉시 실패 처리
- **프롬프트 인젝션 방어**: 세그먼트 텍스트 속 지시문을 명령으로 따르지 않도록 시스템 프롬프트에 명시
- **API 실패 폴백**: Claude 호출 실패 시에도 파이프라인이 죽지 않고 목업으로 안전하게 대체
- **디코딩 안정성**: `condition_on_previous_text=False`로 Whisper의 반복 루프(hallucination loop)를 방지 — 검증 중 실제로 겪은 30분 타임아웃 문제의 해결책
- **임계값 인자화**: 리스크 판정 임계값(부채비율/유동비율)을 코드에 박지 않고 함수 인자로 분리
- **재실행해도 안 덮어쓰는 아카이빙**: 실행마다 `notebooks/runs/<RUN_ID>/`에 음성·STT 결과·리스크 판정을 보존
- **STT 신뢰도 활용**: Whisper의 `avg_logprob`/`no_speech_prob`을 리스크마다 함께 남기고, 낮은 신뢰도 세그먼트를 근거로 썼다면 경고
- **비밀정보 관리**: API 키는 Colab Secrets/환경변수로만 받고 코드·출력·git 이력에 남기지 않음

## 확장 기능 (10~12번 섹션)

- **리스크별 근거 오디오 재생**: 담당 분석가가 타임스탬프를 클릭해 실제 발언을 바로 들어보는 workflow의 최소 구현

세 기능 모두 실행 결과로 검증했고, 이 중 첫 번째 기능을 만드는 과정에서 위 grounding 버그를 발견했습니다. 이번에 구현하지 않은 나머지 확장 아이디어(실시간 스트리밍, 진짜 화자 분리, 도메인 파인튜닝, 톤/감정 분석, GTM, 엔터프라이즈 연동)는 [ROADMAP.md](ROADMAP.md)에 분석으로 정리했습니다.

===== quest_PoC/ROADMAP.md =====
# 확장 로드맵 — 실전 적용을 위해 더 필요한 것

> 이 문서는 코드로 구현하지 않은 항목들을 다룹니다. 인프라·데이터·계정이 없는 상태에서 흉내만 낸 코드를 넣으면 "검증된 것처럼 보이지만 실제로는 검증되지 않은" 결과물이 되기 때문에, 대신 이 PoC로 실제로 확인한 것과 실전에 가려면 무엇이 더 필요한지를 정리합니다. (`APPLICATION_POINTS.md`의 "PoC의 산출물은 판단이다"와 같은 원칙입니다.)

## 1. 실무 프로세스 및 파이프라인 확장성

### 실시간 컨퍼런스콜 처리 (Streaming STT)

**이 PoC에서 확인한 것**: Whisper `small` 모델이 103초 오디오를 29초에 처리합니다(실시간의 약 3.5배 속도). 즉 배치(사후) 처리로도 이미 충분히 빠릅니다.

**실시간으로 바꾸려면 필요한 것**:
- Whisper 자체는 스트리밍 모델이 아닙니다 — 오디오를 청크(예: 5~10초)로 잘라 순차적으로 넣는 방식(`faster-whisper`의 VAD 기반 청크 처리, 또는 `whisper-streaming` 같은 래퍼)으로 흉내 내야 합니다.
- 청크 경계에서 문장이 잘리면 인식률이 떨어집니다 — 겹치는 구간(overlap)을 두고 뒤 청크에서 다시 인식해 합치는 로직이 필요합니다.
- "실시간 팝업 알림"은 이 PoC의 리스크 판정 로직(정규식 임계값 또는 Claude 호출)을 청크마다 반복 실행하는 것으로 확장 가능합니다 — 로직 자체는 이미 사후 처리와 동일하게 재사용할 수 있습니다.

**판단**: 기술적으로 불가능하지 않지만, 이 조직의 실적발표는 분기당 1회(`APPLICATION_POINTS.md` 참고)라 "실시간"의 긴급성이 크지 않습니다. 배치 처리로 몇 분 안에 브리핑이 나오는 지금 방식 대비 실시간 전환의 한계효용은 낮다고 판단합니다.

### 화자 분리(Diarization) 및 발표/Q&A 구별

**이 PoC에서 확인한 것**: `notebooks/earnings_call_briefing_poc.ipynb` 11번 섹션에서, 실제 화자 분리 없이 "질문"이라는 전환 문구로 발표 구간과 질의응답 구간을 나누는 저비용 프록시를 구현했습니다. 이걸로 "이 리스크가 발표 중 나온 것인지 Q&A 중 나온 것인지"는 구분되지만, **발화자가 누구인지**(경영진 vs 애널리스트)는 구분하지 못합니다.

**진짜 화자 분리를 하려면 필요한 것**:
- `pyannote.audio` 같은 화자 분리 모델 — 다만 일부 모델이 AGPL 라이선스이거나 HuggingFace 게이트(토큰 발급) 조건이 있어, 도입 전 라이선스 확인이 먼저입니다(사진 검색기 예시와 같은 원칙).
- 화자 분리 결과와 Whisper 세그먼트를 시간축으로 정렬(alignment)하는 추가 로직.
- "이 화자가 경영진인지 애널리스트인지"는 화자 분리만으로는 알 수 없고, 목소리 등록(enrollment) 또는 "먼저 말하는 사람=경영진" 같은 휴리스틱이 추가로 필요합니다.

**분석 가치**: "경영진이 스스로 인정한 리스크"와 "애널리스트가 지적한 리스크"는 신뢰도가 다릅니다 — 전자는 이미 회사가 알고 대응 중인 이슈, 후자는 시장이 새로 제기한 이슈일 가능성이 높습니다. 브리핑에 이 구분이 있으면 "이미 알려진 리스크"와 "새로 제기된 리스크"를 다르게 우선순위화할 수 있어 실무 가치가 있다고 판단합니다.

## 2. 금융/재무 도메인 특화 및 신뢰성

### 도메인 특화 어휘/파인튜닝 ROI

**이 PoC에서 확인한 것**: `initial_prompt`로 회계 용어 사전을 주입했더니 일부 용어("손익", "총계")는 고쳐졌지만 전부는 아니었습니다("질의응답"→"지류응답", "매출채권"→"매출책권"은 그대로— `VALIDATION_RESULTS.md` 4번 섹션 참고).

**파인튜닝 ROI 판단**:
- Whisper 파인튜닝에는 (a) 라벨링된 회계/재무 도메인 음성-텍스트 쌍 데이터, (b) GPU, (c) 파인튜닝 파이프라인 구축이 필요합니다 — 이 PoC 환경(로컬 CPU)에서는 실행 자체가 불가능합니다.
- 비용 대비 효과: 이번에 남은 오인식은 전부 **리스크 판단에 쓰이는 숫자에는 영향이 없는** 서술어 수준이었습니다. 파인튜닝은 "브리핑 문장이 매끄러운가"에는 도움이 되지만, "리스크를 놓치거나 잘못 판단하는가"에는 이미 영향이 없다는 뜻이라 **우선순위가 낮습니다.**
- 더 저렴한 대안: `initial_prompt`를 문장 형태로 더 구체화하거나(단어 나열이 아니라 실제 대화 예문), STT 이후 LLM 보정 단계를 추가하는 쪽이 파인튜닝보다 비용 대비 효과가 높을 것으로 판단합니다.

### 정확도 가드레일 및 Human-in-the-loop UI

**이 PoC에서 확인한 것**: `segment_confidence`(avg_logprob/no_speech_prob)를 리스크마다 남기고, 10번 섹션에서 근거 구간 오디오를 실제로 잘라 재생하는 기능까지 구현했습니다. **이 기능을 만드는 과정에서 실제로 근거 세그먼트가 잘못 잡혀 있던 버그를 발견해 고쳤습니다** — "1차 스크리닝 + 사람이 타임스탬프로 검증"하는 workflow가 실제로 오류를 잡아낸 사례입니다.

**실전 UI로 만들려면 필요한 것**: 노트북 셀 대신 웹 UI(예: Streamlit)에서 리스크 목록 클릭 → 해당 오디오 재생 + 원문 하이라이트를 보여주는 화면. 코드 로직(세그먼트 찾기, 클립 자르기)은 이미 있으므로 UI 레이어만 얹으면 됩니다 — 공수는 크지 않을 것으로 판단합니다(로직 재사용 가능, 프론트엔드 작업만 추가).

## 3. 멀티모달 융합 및 십자 검증

### 음성-재무제표 수치 대조

**이 PoC에서 확인한 것**: 12번 섹션에서 실제로 구현하고 검증했습니다. 음성에서 뽑은 수치(매출성장률 20%, 부채비율 233%, 유동비율 88.9%)를 정확한 재무제표와 대조하면 불일치가 없고, 일부러 틀리게 만든 재무제표(매출성장률 8%로 변경)와 대조하면 그 불일치를 정확히 잡아냅니다.

## 0. 정확도/누락 개선 2차 반영 (2026-09-26)

1차 검증(아래 1~4번)에서 발견된 문제에 대응해 세 가지를 추가로 반영하고 재검증했습니다.

| 반영한 것 | 목적 |
|---|---|
| Whisper `initial_prompt`에 회계 용어 사전 주입 | 전문용어 오인식 완화 |
| 매칭을 공백 제거 사본(`normalize`)에서 수행하도록 일반화 | Whisper가 "부채비율"→"부채 비율"처럼 임의로 띄어 써서 생기는 누락을 근본적으로 흡수 |
| `condition_on_previous_text=False` | 검증 중 실제로 발생한 문제(아래 참고)를 해결 |

**검증 중 실제로 발생한 문제**: `medium` 모델 비교에 `initial_prompt`를 함께 넣었더니 Whisper가 반복 루프(hallucination loop)에 빠져 **30분 타임아웃**이 발생했습니다. 원인은 `condition_on_previous_text=True`(기본값)가 한 세그먼트의 디코딩 오류를 다음 세그먼트까지 전파시키는, 문서화된 Whisper 불안정성입니다. `condition_on_previous_text=False`로 막았고, 모델 크기 비교는 `initial_prompt` 없이(모델 크기 자체의 영향만 분리해서) 다시 설계했습니다. *이 자체도 "정확도 개선을 시도하다가 실제로 새 문제를 만났고, 원인을 진단해 고친" 사례입니다.*

## 0-1. Grounding 버그 발견 및 수정 (2026-09-27)

리스크별 근거 오디오를 재생하는 기능(3-4번 참고)을 만들다가, **저장된 STT 원본(`stt_result.json`)을 직접 열어 확인**하는 과정에서 실제 버그를 발견했습니다.

**문제**: 근거 세그먼트를 찾는 `find_segment_for(keyword, segments)`가 "부채"/"유동"이라는 **2글자 키워드**로 첫 번째 매칭 세그먼트를 반환하고 있었습니다. 그런데 "부채"라는 글자는 진짜 리스크인 "부채비율"(233%)뿐 아니라, 재무상태표를 읽는 훨씬 이른 구간의 "부채총계"에도 들어 있습니다.

| 리스크 | 실제 발언 위치(진짜 근거) | 수정 전 grounding이 가리키던 곳 | 문제 |
|---|---|---|---|
| 높은 부채비율 (233%) | **68.6~76.5초**: "...현재 부채 비율은 233% 수준으로..." | 37.5~43.5초: "자산 총계는 20만... **부채 총계**는 14만..." | 전혀 다른 발언(재무상태표 낭독)을 근거로 잘못 표시 |
| 단기 유동성 부족 (88.9%) | **76.5~84.4초**: "유동 비율도 88.9%로 100%를 밑돌고..." | 46.7~53.7초: "**유동자산**은 8만... **유동부채**는 9만..." | 마찬가지로 다른 발언을 근거로 잘못 표시 |

**왜 지금까지 몰랐나**: 문자 유사도·WER·다중 시나리오 통과 여부 같은 정량 지표는 전부 "숫자가 맞았는가"만 확인하고 "그 숫자의 근거로 표시된 타임스탬프가 진짜 맞는가"는 확인하지 않았습니다. 이 프로젝트의 핵심 가치인 "타임스탬프 근거"를 실제로 재생해서 듣기 전까지는 드러나지 않는 종류의 버그였습니다.

**수정**: `find_segment_for_value(value_str, segments)`로 교체 — 리스크 제목의 느슨한 키워드 대신, 정규식이 실제로 매칭한 숫자("233", "88.9")가 **"비율"이라는 단어와 함께** 등장하는 세그먼트를 찾습니다. `mock_extract_risks`도 이 값(`matched_value`)을 함께 반환하도록 수정했습니다.

**수정 후 재실행 결과 (실측 확인됨)**:
```json
{
  "title": "높은 부채비율",
  "segment_start": 68.6,
  "grounded": true
}
```
```json
{
  "title": "단기 유동성 부족",
  "segment_start": 76.52,
  "grounded": true
}
```
→ 68.6초, 76.52초 모두 위 표의 "진짜 근거" 구간과 정확히 일치합니다. **동시에, 이 정확한 구간의 STT 신뢰도가 낮게 나와(`no_speech_prob≈0.71`) 3-3번에서 만든 저신뢰도 경고가 이번 실행에서 처음으로 실제 발동했습니다** — 아래 3-4번과 6번에 원본 그대로 남깁니다.

## 0-2. 실제 기업 공개 데이터로 검증 (2026-09-28)

| 항목 | 결과 |

| STT 문자 유사도 (실제 보도자료 원문 대비) | **88.8%** — 가상 대본(89.1%)과 거의 동일 |

**목업 리스크 로직이 아무것도 못 찾은 이유**: 이 보도자료는 사상 최대 실적을 낸 분기라 부채비율·유동비율 같은 리스크 언급이 전혀 없습니다. 우리 목업 로직(`mock_extract_risks`)은 정확히 이 두 지표만 찾도록 좁게 만들어져 있어서, 다른 종류의 실제 공시에는 **일반화되지 않습니다**. 이건 버그가 아니라 목업 로직의 설계 범위 자체가 좁다는 것을 실제 데이터로 재확인한 것입니다 — 실전에서 이 지점을 해결하려면 정규식이 아니라 실제 Claude API 호출(범용 리스크 추출)이 필요합니다(`ROADMAP.md` 참고).

## 3. 추가 검증 (정확도/안정성 강화)

### 3-1. Whisper 모델 크기 비교 (정확도 vs 속도)

같은 오디오를 `base`/`small`/`medium` 세 모델로 각각 전사해 비교했습니다 (`initial_prompt` 없이, 모델 크기 자체의 영향만 분리).

| 모델 | 처리 시간 | 문자 유사도 |
|---|---|---|
| `base` | 9.4~15.3초 | 80.0% |
| **`small` (채택)** | **29.3~64.0초** | **89.1%** |
| `medium` | 305.1~485.6초 (5.1~8.1분) | 91.0% |

**해석**: `medium`이 이번엔 `small`보다 정확도가 약간 높게 나왔지만(91.0% vs 89.1%), **13배 더 느립니다**. `base`는 가장 빠르지만 정확도가 5%p 이상 낮습니다. 실시간성이 중요한 이 유스케이스(수 분 안에 브리핑 확인)에서는 `small`이 여전히 합리적인 균형점입니다. (n=1 샘플 비교라 일반화에는 주의가 필요합니다 — 실제로 이전 실행에서는 `medium`이 `small`보다 근소하게 낮게 나온 적도 있어, 두 모델의 정확도 차이는 이 정도 샘플 크기에서는 오차 범위에 가깝다고 보는 것이 정확합니다.)

### 3-2. 다중 시나리오 검증 — 발견한 버그와 수정 효과의 재확인

샘플 1개만으로는 "우연히 잘 나온 것"인지 확인할 수 없어, 재무 프로필이 다른 시나리오 2개를 추가했습니다.

- **시나리오 B (건전전자)**: 부채비율 43%, 유동비율 300% — 리스크가 전혀 없어야 정상
- **시나리오 C (성장전자)**: 부채비율 233%(위험), 유동비율 166%(정상) — "높은 부채비율"만 탐지되어야 정상

최초 구현(`mock_extract_risks_naive` — "유동비율"/"부채비율"이라는 **단어가 텍스트에 등장하기만 하면** 무조건 리스크로 판단, 공백 처리 없음)과, 실제 수치를 정규식+공백무관 매칭으로 판단하는 수정판을 비교한 결과:

| 시나리오 | 기대 결과 | 수정 전(키워드 매칭) | 수정 후(공백무관 임계값 판정) |
|---|---|---|---|
| A (원본, 리스크 2건) | 유동성 부족 + 높은 부채비율 | ❌ 이번 실행에서는 STT가 "부채 비율"/"유동 비율"로 띄어 써서 **둘 다 누락** | ✅ 일치 |
| B (건전전자, 리스크 0건) | (없음) | ✅ 일치 | ✅ 일치 |
| C (성장전자, 부채비율만) | 높은 부채비율만 | ❌ 누락 | ✅ 일치 |

**의미**: 이번 실행에서는 원본 시나리오 A조차 최초 구현(키워드 매칭)으로는 리스크를 **하나도 탐지하지 못했습니다** — Whisper가 "부채비율"/"유동비율"을 매번 띄어 쓴 탓입니다. 반면 수정판(공백 제거 후 매칭)은 이런 변형과 무관하게 3개 시나리오 모두 정확히 통과했습니다. **이는 "공백-무관 매칭" 수정이 특정 케이스 하나를 땜질한 게 아니라, 실제로 반복 재현되는 근본 문제를 해결했다는 것을 재확인시켜 줍니다.**

### 3-3. 정확도/보안 가드 (코드 레벨)

- **Grounding 검증**: 각 리스크의 근거 타임스탬프가 실제 세그먼트와 일치하는지 코드로 재검증 — 프롬프트로 "원문 인용 기반"을 지시하는 것만으로는 강제되지 않으므로, 할루시네이션을 코드 레벨에서 한 번 더 막습니다.
- **스키마 검증**: LLM/목업 출력이 필수 필드·허용값을 갖췄는지 확인, 어긋나면 즉시 실패시켜 잘못된 데이터가 조용히 흘러가는 것을 방지합니다.
- **프롬프트 인젝션 방어**: 세그먼트 텍스트 안에 지시문처럼 보이는 문장이 있어도 명령으로 따르지 않고 데이터로만 취급하도록 시스템 프롬프트에 명시했습니다.
- **API 실패 폴백**: Claude 호출이 실패(요금 한도·네트워크 오류)해도 파이프라인이 죽지 않고 목업으로 안전하게 대체됩니다.
- **디코딩 안정성**: `condition_on_previous_text=False`로 Whisper의 반복 루프(hallucination loop)를 방지 — 실제로 이 검증 과정에서 겪은 30분 타임아웃 문제의 해결책입니다.
- **임계값 인자화**: `mock_extract_risks`의 판정 임계값(부채비율 200%, 유동비율 100%)을 코드에 박지 않고 함수 인자(`debt_ratio_threshold`, `current_ratio_threshold`)로 뺐습니다. 조직마다 다를 수 있는 리스크 기준을 코드 수정 없이 바꿀 수 있습니다 (`APPLICATION_POINTS.md` 4번 섹션에서 발견한 위반사항을 수정).
- **재실행해도 덮어쓰지 않는 산출물 아카이빙**: 실행마다 `RUN_ID`(타임스탬프)로 `notebooks/runs/<RUN_ID>/` 폴더를 새로 만들고, 그 안에 음성·STT 결과(`stt_result.json`)·리스크 판정(`risks.json`)을 보존합니다. `notebooks/earnings_call.mp3`는 README 등 문서에서 참조하는 최신 스냅샷일 뿐, 감사 기록의 원본은 `runs/` 쪽입니다 (마찬가지로 `APPLICATION_POINTS.md`에서 발견한 위반사항을 수정).
- **비밀정보 관리**: `ANTHROPIC_API_KEY`는 Colab Secrets 또는 환경변수로만 받고, 노트북 출력·git 이력에 남지 않습니다(`.gitignore`로 `.venv/`, `notebooks/runs/` 등 로컬 산출물도 제외).
- **STT 신뢰도 활용**: Whisper가 세그먼트마다 이미 내주는 `avg_logprob`/`no_speech_prob`을 그동안 계산에 안 쓰고 있었습니다. 이제 각 리스크에 근거 세그먼트의 신뢰도(`segment_confidence`)를 함께 남기고, 신뢰도가 낮은 세그먼트(`avg_logprob < -1.0` 또는 `no_speech_prob > 0.5`)를 근거로 삼았다면 경고를 출력합니다. **정직한 한계**: 이번 TTS 기반 클린 음성에서는 모든 세그먼트의 신뢰도가 높게 나와(예: avg_logprob≈-0.23) 실제로 경고가 발동한 적은 없습니다 — 이 코드가 "낮은 신뢰도를 실제로 걸러내는지"는 노이즈가 있는 실제 녹음으로 검증해야 확인됩니다.

### 3-4. 확장 기능 검증 (2026-09-27 추가)

두 가지 실제 예시(사진 검색기, 스쿼트 보조도구) 및 확장 아이디어 논의에서 나온 요청을 반영해 세 기능을 추가하고, 실제로 실행해 검증했습니다. (`ROADMAP.md`에는 이번에 구현하지 않기로 한 나머지 확장 아이디어를 정리했습니다.)

**리스크별 근거 오디오 재생**: 각 리스크의 근거 세그먼트만 잘라 `notebooks/runs/<RUN_ID>/evidence_*.mp3`로 저장하고 노트북에서 재생합니다. 이 기능을 만드는 과정에서 0-1번의 grounding 버그를 발견했습니다 — "검산 기능을 만드는 행위 자체가 검산이었다"는 두 예시의 교훈을 그대로 재현한 셈입니다.

**발표 vs 질의응답(Q&A) 구간 분리**: 진짜 화자 분리 없이, "질문"이라는 전환 문구(정확히 인식되는 단어를 선택 — "질의응답"은 매번 "지류응답"으로 오인식되어 마커로 쓰지 않았습니다)를 기준으로 구간을 나눴습니다. 실행 결과:

```
질의응답 구간 시작 추정 시각: 56.88초
[발표(Presentation)] 리스크 0건
[질의응답(Q&A)] 리스크 2건
  - 단기 유동성 부족 (76.5s)
  - 높은 부채비율 (68.6s)
```

두 리스크 모두 Q&A 구간(애널리스트 질문에 대한 경영진 답변)에서 나온 것으로 정확히 분류됐습니다 — 실제로 대본상 두 수치 모두 질의응답 중 언급되므로 맞는 결과입니다. **한계**: 발화자가 누구인지는 모르므로 "경영진이 먼저 밝힌 리스크"와 "애널리스트가 캐물어서 나온 리스크"는 구분하지 못합니다.

**음성-재무제표 십자 검증**: 음성에서 뽑은 수치를 (1) 정확한 재무제표, (2) 일부러 틀리게 만든 재무제표와 각각 대조했습니다. 실행 결과:

```
음성에서 추출한 수치: {'매출_성장률': 20.0, '부채비율': 233.0, '유동비율': 88.9}
[정확한 재무제표] 대조 결과:
  불일치 없음
[오타가 있는 재무제표(가정)] 대조 결과:
  ⚠️ 매출_성장률: 음성=20.0 vs 재무제표=8
```

같은 파이프라인이 정확한 재무제표와는 일치하고, 의도적으로 틀리게 만든 재무제표(매출 성장률 8%로 변경)와는 그 불일치를 정확히 잡아냈습니다.

## 4. Failure case — STT 자체의 한계 (2차 반영 후에도 남은 것)

| 매출채권 | 매출책권 | 매출책권 | ➖ 그대로 |
| 재무건전성 | (관찰 안 됨) | 제무 권전성 | ⚠️ 새로 관찰됨 |

**중요한 점**: 위 오인식은 모두 서술어·용어 표현에 국한되었고, **리스크 판단에 실제로 쓰이는 숫자(부채비율 233%, 유동비율 88.9%, 매출 성장률 20% 등)는 5개 항목 모두 정확히 인식**되었습니다(1번 섹션 참고).

**다음 단계로 시도해볼 만한 것** (아직 반영 안 함)
- STT 이후 LLM 보정 단계 추가: Claude에게 "발음이 비슷한 재무 용어로 보정"하도록 지시하는 후처리 — "지류응답"처럼 문맥상 명백한 오류를 의미 기반으로 교정할 가능성이 높습니다.
- `initial_prompt`에 더 구체적인 예문(단어 나열이 아니라 실제 문장 형태)을 넣어 언어모델이 문맥까지 학습하도록 유도.
- 실제 컨퍼런스콜은 배경 소음·다수 화자가 섞여 있어, 이번 TTS 기반 클린 음성보다 정확도가 낮아질 가능성이 있습니다 (화자 분리는 이번 PoC 범위 밖).

# 할 일 목록 (Todo List) — Supabase 백엔드 튜토리얼

Supabase(Postgres + 자동 REST API)를 백엔드로 사용하는 순수 HTML/JS 할 일 목록 앱입니다.

## 사용 기술
- 프론트엔드: HTML / CSS / JavaScript (빌드 도구 없음)
- 백엔드: [Supabase](https://supabase.com) — DB, 인증, API를 무료로 제공하는 서비스
- 배포: GitHub Pages

## 로컬에서 실행하기
1. Supabase 프로젝트를 만들고 `setup.sql`을 SQL Editor에서 실행합니다.
2. `config.js`에 내 프로젝트의 Project URL과 anon public key를 채워 넣습니다.
3. `index.html`을 브라우저로 엽니다 (별도 서버 불필요).

## 개선한 부분
- 튜토리얼 기본 기능(추가/조회/완료 체크)에 더해 **삭제**와 **키워드 검색**을 직접 추가했습니다. 검색은 매 입력마다 DB를 다시 조회하지 않고, 이미 불러온 목록을 클라이언트에서 필터링하도록 구현했습니다.

## 배포 링크
- https://rubilisa08.github.io/to-do-list/

## 보안 체크
- **비밀값을 코드에 직접 안 적었는가?** `config.js`에 있는 값은 Supabase의 **anon public key**로, 애초에 브라우저에 노출되도록 설계된 키입니다 (실제 접근 제어는 키가 아니라 아래 RLS 정책이 담당). 진짜 비밀 키인 **service_role key**는 이 정도 권한을 우회할 수 있어서 절대 프론트엔드 코드에 넣지 않았습니다 — 필요했다면 Supabase Edge Function 같은 서버 쪽 코드에서만 써야 합니다.
- **검증을 백엔드에서 하는가?** `setup.sql`의 `check (char_length(trim(task)) > 0 and char_length(task) <= 200)` 제약으로, 브라우저의 `required` 속성을 우회해서 API를 직접 호출해도 빈 값이나 너무 긴 값은 DB가 거부합니다.
- **RLS를 켜고 정책을 넣었는가?** `alter table todos enable row level security`로 켜고, `anon` 역할에 대해 select/insert/update/delete를 명시적으로 허용하는 정책 4개를 넣었습니다. RLS를 안 켜면 anon key만으로 테이블 전체를 무제한 접근할 수 있어 위험합니다.
- **로그인 데이터에 인가가 들어가는가?** 이 앱은 로그인 없이 누구나 같은 목록을 보고 고치는 공개 데모라서 사용자별 인가는 적용하지 않았습니다 (의도적 범위 제한이지, 빠뜨린 게 아닙니다). 사용자별 할 일 목록으로 확장하려면 Supabase Auth로 로그인을 추가하고, `todos`에 `user_id` 컬럼을 두고 정책을 `using (auth.uid() = user_id)`로 바꾸면 됩니다.
- **무료 티어 한도를 아는가?** Supabase 무료 플랜은 프로젝트당 DB 500MB, 월 5GB 대역폭이 한도이고, 카드 등록 없이 시작하면 자동 과금 위험이 없습니다. 다만 무료 프로젝트는 1주일 이상 활동이 없으면 자동 일시정지되니, 오래 방치하면 다시 Resume 해줘야 합니다.
