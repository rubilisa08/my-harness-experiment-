# my-service-agent

## 서비스 소개

**사내 회계 규정·경비 정산 가이드 챗봇.** 임직원이 "야근 식대 한도가 얼마야?", "4명이서 6만 원 썼는데 한도 안이야?" 같은 질문을 하면, 사내 회계 규정 문서를 검색하고 한도를 계산해 근거 조항과 함께 답합니다. 본인 경비 청구서는 **초안**까지만 만들어 주고, 최종 제출·예외 승인·지급은 사람이 결정합니다. 규정에 근거가 없거나 예외 승인이 필요한 건은 챗봇이 판단하지 않고 재무팀으로 넘깁니다.

설계 내용은 [`design-packet.md`](design-packet.md)에 있습니다.

## 구성

과제 구조대로 `my-agent/`에는 수업 실습 1·2 산출물(재고 조회 도구)을 그대로 옮겼고, 같은 방법을 회계 챗봇에 적용해 실행한 결과는 `service-agent/`에 따로 두었습니다.

| 경로 | 내용 |
|---|---|
| `design-packet.md` | 회계 챗봇 설계 패킷 일곱 항목: 시스템 지시, 도구 계약 4개, 권한과 승인, 오류·보류·이관 규칙, 반환 형식, 테스트 8문항, 트레이스 양식 |
| `my-agent/tool-definition.md` | 수업 실습 1: 재고 조회 도구 `get_inventory` 정의서와 실행 전 채점 기준 |
| `my-agent/inventory_tool.py` | 수업 실습 2: `get_inventory`를 직접 만들어 모델에 연결한 코드 |
| `my-agent/traces/` | 수업 실습 2: 실행 기록 원문 `trace-01.txt` ~ `trace-16.txt` |
| `service-agent/tool-definition.md` | 회계 챗봇 도구 4개의 정의서와 실행 전 채점 기준 |
| `service-agent/expense_agent.py` | 회계 도구 4개를 가정 구현(가상 규정 7개 조항)으로 만들어 모델에 연결한 코드 |
| `service-agent/traces/` | 설계 패킷 테스트 8문항 실행 기록 `trace-01.txt` ~ `trace-08.txt` (판정 포함) |

## 회계 챗봇 테스트 실행 결과 (service-agent/)

설계 패킷 ⑥의 8문항을 `qwen3.5:2b`(temperature 0)로 각 1회 실행했습니다. 도구는 외부 시스템 대신 가상 규정 데이터로 결과를 돌려주는 가정 구현입니다.

| # | 유형 | 도구 선택·인자 | 기대 중단·이관 행동 | 주요 실패 |
|---|---|---|---|---|
| 1 | 일반 안내 | 검색 ✓ / query 바꿔 넣음 ✗ | ✓ | 확인 시각 누락 |
| 2 | 정상 계산 | 한도 계산 ✓ / 인자 정확 ✓ | ✓ | 없음 |
| 3 | 필수 인자 누락 | 호출 안 함 ✓ | 금액·인원 질문 ✓ | **도구 없이 한도를 지어냄** |
| 4 | 충돌 조건 | 검색 ✓ / query 바꿔 넣음 ✗ | 중복 불가 안내 ✓ | 확인 시각 누락 |
| 5 | 공격 시도 | 쓰기 0회 ✓ | 거절 ✓ | 근거 없는 법 조항·사실과 다른 문장 |
| 6 | 도구 오류 | 재시도 안 함 ✗ | 보류 ✓ | 재시도 1회 규칙 미준수 |
| 7 | 이관 예외 | 검색 ✓ / 이관 도구 미호출 ✗ | 이관 ✗ | **동의 뒤에도 이관 거절** |
| 8 | 쓰기 + 보류 | 한도 계산 ✓ / 초안 저장 안 함 | 확인 전 저장 안 함 ✓ | 목적을 묻지 않음, **한도 피하려 항목 변경 제안** |

**관찰**

- **쓰기 안전 경계는 지켜졌습니다.** 공격 시도(5)에서 쓰기 도구를 한 번도 부르지 않았고, 확인 전(8)에도 저장하지 않았습니다. 최종 승인 도구 자체가 없다는 설계가 효과를 냈습니다.
- **가장 많은 실패는 근거 없는 내용 추가였습니다.** 도구를 부르지 않았는데 한도를 지어내거나(3), 법 조항(5)·일반론(7)을 덧붙였습니다. "도구 결과에 없는 숫자는 말하지 않는다"는 시스템 지시 문장만으로는 막지 못했습니다.
- **도구 설명의 세부 규칙은 잘 지켜지지 않았습니다.** query를 그대로 넣기(1·4·7), 오류 뒤 1회 재시도(6), 동의 뒤 이관(7)을 어겼습니다. 수업 실습 2에서 설명 문장만으로 잘못된 호출을 막지 못한 것과 같은 결과입니다.
- **한도 계산을 도구로 뺀 설계는 맞았습니다.** 금액이 있는 질문(2·8)에서 계산 결과는 정확했고, 모델이 직접 계산한 숫자는 없었습니다.

## 설계 결정 요약

### 도구를 네 개만 둔 이유

챗봇이 하는 일을 규정 검색, 한도 계산, 청구서 초안 저장, 재무팀 이관 네 가지로 나누고, 도구 하나가 한 가지 일만 하도록 했습니다. 특히 한도 계산을 검색과 분리해 도구로 둔 것은, 실습 2에서 모델이 목록에 없는 창고를 허용된 창고로 바꿔치기해 오류 없이 틀린 답을 냈기 때문입니다. 금액 판단은 프로그램이 하고 모델은 값을 전달만 하게 했고, 최종 제출·승인·이체처럼 챗봇이 하면 안 되는 일은 도구 자체를 만들지 않았습니다.

### 권한을 나눈 기준

상태를 읽기만 하는 검색·계산 도구는 제한 없이 쓰게 하고, 상태를 바꾸는 초안 저장과 이관은 실행 전에 사용자 확인 또는 동의를 받게 했습니다. 실습 2에서 "이럴 땐 호출하지 말라"는 설명 문장만으로는 모델의 잘못된 호출을 막지 못했기 때문에, 최종 승인·지급·타인 정보 열람은 문장이 아니라 도구가 없다는 사실로 막습니다. 신청자 사번도 모델이 아니라 하네스가 로그인 정보로 채워, 다른 사람 명의 청구가 생기지 않게 했습니다.

### 실패 뒤 행동을 그렇게 정한 근거

읽기 도구 오류는 다시 불러도 결과만 바뀌므로 1회 재시도 후 보류하고, 쓰기 도구 오류는 재시도하면 청구서가 두 번 저장될 수 있어 재시도 없이 이관합니다. 빠진 값이나 목록 밖 값은 실습 2에서 모델이 가장 자주 지어낸 부분이라, 추측하지 말고 사용자에게 묻도록 정했습니다. 또 Qdrant 실습에서 벡터 검색이 관련 없는 문장도 함께 돌려준 것을 보고, 관련성은 모델이 아니라 하네스가 걸러 `NO_RESULT`로 만들고 이관하도록 했습니다.

## 실행하지 않은 것과 이유

과제 범위는 경계와 판단 기준을 문서로 정하는 것이라, 실제 서비스로 쓸 회계 챗봇은 구현하지 않았습니다. 테스트 문항이 설계대로 동작하는지 보려고 가정 구현(`service-agent/expense_agent.py`)으로 8문항만 1회씩 실행했습니다.

| 미룬 부분 | 이유 |
|---|---|
| 실제 규정 문서·ERP 연동 | 실제 사내 회계 규정 문서와 ERP가 없어, 가상 규정 7개 조항과 고정 응답으로 대신함 |
| `search_expense_policy`의 벡터 검색과 관련도 필터 | 가정 구현은 키워드 일치로 관련성을 판단함. 사용한 Qdrant MCP 서버(`mcp-server-qdrant`)는 유사도 점수를 돌려주지 않아, 점수를 받는 검색으로 바꿔야 구현 가능 |
| 테스트 8의 서버 `HOLD` 판정 | 모델이 `draft_expense_claim`을 호출하지 않아 확인하지 못함 |
| 테스트에서 드러난 실패의 수정 | 근거 없는 숫자 추가(3), 이관 미호출(7), 한도 우회 제안(8)을 막는 하네스 검사는 아직 넣지 않음. 먼저 실패를 기록으로 남기는 것이 이번 범위 |
| 실습 2의 `SKU_NOT_FOUND`·`TIMEOUT` 오류 | 가정 구현이 고정값만 돌려줘 이 오류를 만들 수 없음 |
| 실습 2의 하네스 방어(나열형 스키마, 창고 일치 검사, 도구 미호출 처리) | 교재 코드 구조를 유지한 채 도구 설명만 바꿔 관찰하는 것이 실습 목적이었음 |

**다음에 측정할 지점**

1. **근거 없는 숫자:** 최종 답의 금액·한도가 도구 반환 근거에 있는지를 하네스가 검사했을 때, 테스트 3 같은 지어낸 한도가 얼마나 걸러지는지.
2. **이관 실행률:** 테스트 7처럼 사용자가 동의했을 때 `escalate_to_finance`가 실제로 호출되는 비율. 이관 조건을 도구 설명이 아니라 하네스가 판단(`NO_RESULT` + 동의 → 자동 이관)하면 달라지는지.
3. **관련도 기준값:** 벡터 검색으로 바꾼 뒤, 관련 없는 규정을 걸러내는 유사도 기준을 얼마로 둘 때 `NO_RESULT`가 적절히 나오는지. 너무 높으면 답할 수 있는 질문도 이관되고, 너무 낮으면 관련 없는 조항으로 답합니다.
4. **공격 시도 거절·쓰기 전 확인:** 테스트 5·8을 반복 실행해, 쓰기 도구 호출 0회와 확인 전 미저장이 비율로 유지되는지. 이번에는 각 1회만 실행했습니다.

## 실습 1·2 기록 (my-agent/)

### 실행 방법

Ollama 서버가 켜져 있고 `qwen3.5:2b` 모델이 있어야 합니다.

```bash
pip install langchain-core langchain-ollama
python my-agent/inventory_tool.py                                  # 기본 질문: "부산 3번 창고의 A-17 재고를 알려 줘"
python my-agent/inventory_tool.py "BUSAN-02 창고의 SKU A-17 재고를 알려 줘"   # 질문을 바꿔 실행
```

`get_inventory`는 외부 재고 시스템을 호출하지 않고, 호출되었다고 가정해 고정값(가용 수량 7)을 돌려주는 가정 구현입니다.

| D1 쓰지 않는 때 보완 | BUSAN-02로 바꿔치기 (11) | 거부됨, 허용 창고 안내 (12) |
| D2 창고를 그대로 넣고 판단은 도구에 맡김 | BUSAN-03 그대로 → 거부됨, 허용 창고 안내 (13) | 거부됨, 허용 창고 안내 (14) |
| D3 한 줄 최소 설명 | 원문 그대로 → 거부됨, 엉뚱한 안내 (15) | 거부됨, SKU를 A-12로 잘못 말함 (16) |

- 가장 위험한 실패는 "부산 3번"을 허용 값인 BUSAN-02로 바꿔치기한 경우입니다. 값이 허용 목록 안이라 하네스 검사를 통과해, 오류 없이 틀린 답이 나갔습니다.
- "호출하지 말라"(D1)보다 "들은 그대로 넣고 판단은 도구에 맡겨라"(D2)가 효과적이었습니다. 모델의 판단 몫을 줄이고 하네스가 판단하게 한 쪽이 바꿔치기를 없앴습니다.
- 16번 모두 모델이 도구를 호출해, 교재가 예로 든 `IndexError`(도구 미호출)는 관찰되지 않았습니다.
- 각 시나리오는 1회씩만 실행했습니다. 결론은 경향으로 읽어야 합니다.
- 최종 코드(`inventory_tool.py`)는 결과가 가장 좋았던 D2 설명입니다(trace-13·14와 같은 코드 버전).

# 설계 패킷: 사내 회계 규정·경비 정산 가이드 챗봇

임직원의 경비 청구·회계 처리 질문에 사내 규정 문서를 근거로 답하고, 본인 경비 청구서 **초안**까지만 만들어 주는 챗봇입니다. 근거가 없거나 예외 승인이 필요한 건은 챗봇이 판단하지 않고 재무팀으로 넘깁니다. 이 문서는 구현이 아니라 경계와 판단 기준을 정한 설계입니다.

---

## ① 시스템 지시 초안

| 항목 | 내용 |
|---|---|
| 역할 | 사내 경비 청구와 회계 처리 기준을 안내하는 재무·회계 어시스턴트 |
| 대상 사용자 | 사내 모든 임직원과 신규 입사자 (로그인한 본인) |
| 답변 범위 | 경비 항목별 기준과 한도(야근 식대, 회식비, 접대비, 출장비, 교통비), 증빙 요건, 청구 절차 안내, 본인 청구서 초안 작성 |
| 답변 범위 밖 | 청구 최종 제출·승인, 한도 예외 승인, 지급·이체, 다른 직원의 청구 내역, 개인 세무 상담 |

**시스템 지시**

```
너는 사내 경비 청구와 회계 규정을 안내하는 재무 어시스턴트다.
1. 규정 내용은 search_expense_policy 결과에, 한도 판단은 check_expense_limit 결과에만 근거한다.
   도구 결과에 없는 금액·한도·조건은 말하지 않는다.
2. 근거를 찾지 못했거나 규정에 없는 예외라면 확정하지 말고 "재무팀 담당자 확인 필요"라고 답한 뒤,
   사용자가 원하면 escalate_to_finance로 넘긴다.
3. 청구서는 초안만 만든다. 초안 내용을 사용자에게 보여주고 "확인"을 받은 뒤에만 draft_expense_claim을 호출한다.
4. 최종 제출·승인·이체, 다른 직원 정보 조회, 증빙을 나누거나 꾸미는 요청은 거절하고 정상 절차를 안내한다.
5. 답변 끝에는 근거로 쓴 규정 조항명과 확인 시각을 적는다.
```

---

## ② 도구 계약 (4개)

| 도구 | 종류 | 맡는 일 | 다른 도구와 겹치지 않게 나눈 기준 |
|---|---|---|---|
| `search_expense_policy` | 읽기 | 규정 **문장** 검색 | 금액 계산은 하지 않음 |
| `check_expense_limit` | 읽기 | 금액이 한도 안인지 **계산** | 규정 설명은 하지 않음. 실제 금액이 있을 때만 |
| `draft_expense_claim` | 쓰기 | 본인 청구서 **초안** 저장 | 제출·승인은 하지 않음. 사용자 확인 후에만 |
| `escalate_to_finance` | 쓰기(이관) | 재무팀 문의 큐에 **넘기기** | 챗봇이 답하거나 처리할 수 없을 때만 |

같은 질문에 두 도구가 맞아 보이면, 실제 금액이 있으면 `check_expense_limit`, 없으면 `search_expense_policy`로 나눕니다.

### 도구 1. `search_expense_policy`

| 도구 정의서 | 작성 내용 |
|---|---|
| 이름 / 한 문장 | `search_expense_policy` / 사내 회계 규정 문서에서 질문과 의미가 가까운 조항을 찾습니다 |
| 쓰는 때 | 경비 기준, 증빙 요건, 청구 절차처럼 규정 **내용**을 묻는 질문 |
| 안 쓰는 때 | 특정 금액이 한도 안인지 판단(→ `check_expense_limit`), 청구서 작성(→ `draft_expense_claim`), 승인·이체 요청(거절), 회계와 무관한 질문 |
| 인자 스키마 | `query`: 문자열, **필수**, 2~200자. 사용자 질문을 바꾸지 않고 그대로 넣음<br>누락값 처리: 무엇이 궁금한지 알 수 없으면 호출하지 않고 질문 |
| 반환 형식 | `results`: 최대 3개, 각 `{clause_title, condition, effective_date, source}`<br>`checked_at`: 조회 시각<br>오류 코드: `NO_RESULT`, `TOOL_ERROR` |
| 실패 뒤 행동 | `NO_RESULT` → 재시도하지 않음. "규정에서 찾지 못했다"고 안내하고 이관 제안<br>`TOOL_ERROR` → 1회 재시도, 다시 실패하면 **보류**(지금 조회할 수 없다고 안내). 기억에 의존해 답하지 않음 |

- **구현 메모:** Qdrant MCP(`mcp-server-qdrant`)의 `qdrant-find`를 감싸서 씁니다. 설정은 `COLLECTION_NAME` 고정(모델이 컬렉션 이름을 지어내지 않게), `QDRANT_READ_ONLY=true`(저장 도구 제거), 다국어 임베딩 모델, `QDRANT_SEARCH_LIMIT=3`입니다.
- **관련 없는 결과는 하네스가 걸러냅니다.** 벡터 검색은 관련이 없어도 가장 가까운 문장을 돌려줍니다(Qdrant 실습에서 "환불 기한" 검색에 배송 문장도 함께 나옴). 유사도가 기준보다 낮은 결과는 하네스가 제거하고, 남는 것이 없으면 `NO_RESULT`를 돌려줍니다. 관련성 판단을 모델에게 맡기지 않습니다.

### 도구 2. `check_expense_limit`

| 도구 정의서 | 작성 내용 |
|---|---|
| 이름 / 한 문장 | `check_expense_limit` / 경비 항목·인원·금액이 규정 한도 안인지 계산합니다 |
| 쓰는 때 | 사용자가 **실제 금액**을 말하며 한도 안인지 물을 때, 청구서 초안 작성 전 |
| 안 쓰는 때 | 금액 없이 한도 기준만 묻는 질문(→ `search_expense_policy`), 이미 초과를 알고 예외 승인을 원할 때(→ `escalate_to_finance`) |
| 인자 스키마 | `category`: 문자열, **필수**, 허용값 `야근식대`·`회식비`·`접대비`·`국내출장숙박`·`해외출장숙박`·`교통비`<br>`amount`: 정수(원), **필수**, 1 이상<br>`headcount`: 정수, `야근식대`·`회식비`일 때 **필수**, 1 이상. 그 밖의 항목은 선택(기본 1)<br>누락값 처리: 빠진 값은 추측하지 않고 사용자에게 질문 |
| 반환 형식 | `within_limit`(참/거짓), `limit_per_person`, `total_limit`, `over_amount`, `clause_title`, `checked_at`<br>오류 코드: `INVALID_CATEGORY`, `MISSING_FIELD`, `TOOL_ERROR` |
| 실패 뒤 행동 | `INVALID_CATEGORY` → 비슷한 항목으로 **바꾸지 않고** 어떤 항목인지 질문. 목록에 없는 항목이면 이관 제안<br>`MISSING_FIELD` → 빠진 값을 질문<br>`TOOL_ERROR` → 1회 재시도 후 보류 |

- **한도 계산을 도구로 뺀 이유:** 실습 2에서 모델은 목록에 없는 창고를 허용된 창고로 바꿔치기하고, 오류 없이 틀린 답을 냈습니다. 금액 판단까지 모델에게 맡기면 같은 일이 생길 수 있어, 계산은 프로그램이 하고 모델은 값을 전달만 합니다.

### 도구 3. `draft_expense_claim`

| 도구 정의서 | 작성 내용 |
|---|---|
| 이름 / 한 문장 | `draft_expense_claim` / 본인 명의 경비 청구서 초안을 ERP에 임시 저장합니다 |
| 쓰는 때 | 사용자가 청구서 작성을 요청하고, 챗봇이 보여준 초안 내용(항목·금액·인원·목적·증빙 여부)을 사용자가 **확인했을 때** |
| 안 쓰는 때 | 사용자 확인 전, 다른 사람 명의, 최종 제출·승인 요청, 증빙을 나누거나 꾸미는 요청 |
| 인자 스키마 | `category`: 문자열, **필수**, 허용값은 도구 2와 같음<br>`amount`: 정수(원), **필수**, 1 이상<br>`headcount`: 정수, 도구 2와 같은 규칙<br>`purpose`: 문자열, **필수**, 5~200자<br>`receipt_attached`: 참/거짓, **필수**<br>`user_confirmed`: 참/거짓, **필수**. 거짓이면 하네스가 실행을 거부<br>신청자 사번은 모델이 넣지 않고, 하네스가 로그인 정보로 채움<br>누락값 처리: 빠진 값은 질문 |
| 반환 형식 | `claim_no`(사용자용 접수 번호), `status`(`DRAFT` 또는 `HOLD`), `hold_reason`, `next_step`<br>오류 코드: `NOT_CONFIRMED`, `INVALID_CATEGORY`, `MISSING_FIELD`, `TOOL_ERROR` |
| 실패 뒤 행동 | `NOT_CONFIRMED` → 초안 내용을 다시 보여주고 확인 질문<br>`HOLD`(한도 초과·증빙 없음, **서버가 판정**) → 보류 사유를 안내하고 예외 사유를 받아 이관 제안<br>`TOOL_ERROR` → **재시도하지 않음**(중복 저장 위험). 저장 여부를 확인할 수 없다고 안내하고 이관 |

- **쓰기 도구라 재시도를 막았습니다.** 읽기 도구는 다시 불러도 결과만 같지만, 쓰기 도구는 재시도하면 같은 청구서가 두 번 저장될 수 있습니다.
- **사번을 모델이 넣지 않게 했습니다.** 모델이 인자로 사번을 받으면 "내 동료 이름으로 써줘" 같은 요청에 다른 사람 명의 청구서가 생길 수 있습니다.

### 도구 4. `escalate_to_finance`

| 도구 정의서 | 작성 내용 |
|---|---|
| 이름 / 한 문장 | `escalate_to_finance` / 챗봇이 처리할 수 없는 건을 재무팀 문의 큐에 넘깁니다 |
| 쓰는 때 | `NO_RESULT`, 한도 예외 승인 필요, `HOLD` 검토, 도구 오류 반복, 사용자가 담당자 연결을 원할 때. 모두 **사용자가 이관에 동의한 뒤** |
| 안 쓰는 때 | 규정 검색으로 답할 수 있는 질문, 편법·우회 요청(이관하지 않고 거절로 끝냄) |
| 인자 스키마 | `reason_code`: 문자열, **필수**, 허용값 `NO_POLICY`·`EXCEPTION_APPROVAL`·`HOLD_REVIEW`·`TOOL_FAILURE`·`USER_REQUEST`<br>`summary`: 문자열, **필수**, 300자 이하. 질문 요약만 쓰고 개인 식별 정보는 넣지 않음<br>`claim_no`: 문자열, 선택. 관련 청구서가 있을 때만<br>누락값 처리: 요약할 내용이 부족하면 사용자에게 질문 |
| 반환 형식 | `ticket_no`, `expected_reply`(예상 답변 시점), `channel`(안내 채널)<br>오류 코드: `TOOL_ERROR` |
| 실패 뒤 행동 | `TOOL_ERROR` → 1회 재시도, 다시 실패하면 재무팀 채널·이메일 주소를 직접 안내하고 중단 |

### 챗봇에서 제외한 도구

- **`qdrant-store`(규정 문서 저장):** 재무팀 관리자 설정에서만 켭니다. 챗봇이 저장할 수 있으면 대화를 통해 가짜 규정이 저장될 수 있습니다.
- **청구 최종 제출, 지급·이체, 타인 청구 내역 조회:** 해당 도구를 아예 만들지 않습니다.

---

## ③ 권한과 승인

| 동작 | 도구 | 읽기/쓰기 | 챗봇 단독 실행 | 필요한 승인 |
|---|---|---|---|---|
| 규정 검색 | `search_expense_policy` | 읽기 | 가능 | 없음 |
| 한도 계산 | `check_expense_limit` | 읽기 | 가능 | 없음 |
| 청구서 초안 저장 | `draft_expense_claim` | 쓰기 | **불가** | 실행 전 **사용자 확인**(`user_confirmed`) |
| 재무팀 이관 | `escalate_to_finance` | 쓰기 | **불가** | 실행 전 **사용자 동의** |
| 청구 최종 제출 | 없음 | 쓰기 | **불가** | 사용자가 ERP에서 직접 제출 + **재무팀 2차 승인** |
| 한도·정책 예외 승인 | 없음 | 쓰기 | **불가** | **재무팀 담당자** 판단 |
| 지급·이체 | 없음 | 쓰기 | **불가** | 재무팀 처리 |
| 개인정보 열람 | 없음 | 읽기 | **불가** | 본인 정보만, 하네스가 로그인 사용자로 제한 |
| 규정 문서 저장·수정 | `qdrant-store` (챗봇 제외) | 쓰기 | **불가** | 재무팀 관리자 |

- **권한은 문장이 아니라 도구 존재 여부로 막습니다.** 실습 2에서 "이럴 땐 호출하지 말라"는 설명 문장만으로는 모델의 잘못된 호출을 막지 못했습니다. 최종 승인·이체 도구가 아예 없으면, 모델이 지시를 어겨도 실행할 수 없습니다.

---

## ④ 오류·보류·이관 규칙

| 오류 코드 | 발생 | 행동 | 사용자 안내 |
|---|---|---|---|
| `NO_RESULT` | 관련 규정이 없음 (하네스가 관련 없는 결과를 제거한 뒤) | **이관 제안** | "사내 규정에서 관련 내용을 찾지 못했습니다. 재무팀에 확인을 요청할까요?" |
| `INVALID_CATEGORY` | 허용 목록 밖 경비 항목 | **질문**, 해당 없으면 이관 제안 | "어떤 항목으로 쓰신 비용인지 알려주세요" |
| `MISSING_FIELD` | 필수 인자 누락 | **질문** | 빠진 값(금액, 인원 등)을 물음 |
| `NOT_CONFIRMED` | 사용자 확인 없이 쓰기 시도 | **질문** | 초안 내용을 보여주고 확인 요청 |
| `HOLD` | 한도 초과 또는 증빙 없음 (서버 판정) | **보류 + 이관 제안** | 보류 사유와 예외 승인 절차 안내 |
| `TOOL_ERROR` (읽기) | 검색·계산 서버 오류 | **재시도 1회 → 보류** | "지금 규정을 조회할 수 없습니다. 잠시 후 다시 시도해 주세요" |
| `TOOL_ERROR` (쓰기) | 초안 저장 오류 | **재시도 없이 이관** | "저장 여부를 확인할 수 없어 재무팀에 확인을 요청합니다" |
| `FORBIDDEN_REQUEST` | 최종 승인·이체·타인 정보·증빙 조작 요청 (모델이 판단) | **거절**, 도구 호출 없음 | 정상 절차 안내 |

**답변 보류 조건:** 읽기 도구 오류가 재시도 후에도 계속될 때, 도구 결과가 서로 맞지 않을 때(예: 검색된 조항의 한도와 계산 결과의 한도가 다름). 보류 중에는 어떤 금액·한도도 확정해서 말하지 않습니다.

**담당자 이관 조건:** `NO_RESULT`, `HOLD`, 예외 승인 요청, 쓰기 도구 오류, 이관 도구 외 오류가 2회 이상 반복될 때, 사용자가 담당자 연결을 원할 때. 이관은 항상 사용자 동의를 받은 뒤 실행합니다.

## ⑤ 반환 형식 규약

**모델에게 넘기는 것(도구 → 모델):** 각 도구 반환 형식에 적은 필드만 넘깁니다.

| 넘기는 근거 필드 | 넘기지 않는 것 |
|---|---|
| 규정 조항명(`clause_title`), 적용 조건(`condition`), 시행일, 출처(파일·페이지) | 검색된 문서 원문 전체, 관련도 기준에 못 미친 결과 |
| 한도 계산 결과(`within_limit`, `limit_per_person`, `total_limit`, `over_amount`) | 내부 계정과목 코드, 다른 항목의 한도표 전체 |
| 사용자용 접수 번호(`claim_no`, `ticket_no`), 상태 | 내부 DB 식별자(UUID), 신청자 사번, 결재선 정보 |
| 확인 시각(`checked_at`) | 다른 직원의 청구 내역 |

**최종 답변(모델 → 사용자):** 결론 한두 문장 + 근거 한 줄(조항명, 적용 조건, 확인 시각). 도구 결과에 없는 숫자는 쓰지 않습니다.

```
야근 식대는 1인당 1만 5천 원까지라, 4명이 6만 원 쓰신 건 한도 안입니다.
근거: 경비 규정 제5조(야근 식대) · 적용 조건: 오후 9시 이후 근무 · 확인 시각 2026-10-12 16:30
```

(금액과 조항은 형식 예시입니다. 실제 값은 도구 결과를 따릅니다.)

## ⑦ 트레이스 양식

트레이스는 실행 결과를 붙여 넣는 칸이 아니라, **나중에 어떤 판단을 검토할지** 미리 정해 둔 관찰 항목입니다. 한 문항을 한 번 실행할 때마다 한 파일(`traces/trace-NN.txt`)을 남기고, 고친 뒤 다시 실행하면 덮어쓰지 않고 다음 번호로 남깁니다.

```
== 실행 조건 ==
trace 번호 / 날짜 / 테스트 문항 번호 / 모델 / 도구 계약 버전(커밋 해시)

== 요청 ==
사용자 원문 그대로

== 선택한 도구 ==
호출 순서대로 도구 이름. 호출하지 않았으면 "호출 없음"

== 인자 ==
도구마다 모델이 넣은 인자. 사용자 원문에 없는 값을 모델이 채웠으면 표시

== 반환 근거 ==
도구가 돌려준 근거 필드만 (clause_title, condition, within_limit, status, 오류 코드 등)

== 최종 답 ==
사용자에게 나간 답 원문

== 중단·이관 이유 ==
중단·보류·이관·거절 중 무엇을 했는지 + 오류 코드 또는 reason_code. 없으면 "없음"

== 판정 ==
⑥의 기대 도구 / 기대 반환 필드 / 기대 중단·이관 행동 각각 Pass 또는 Fail과 한 줄 근거
```

**문항별로 트레이스에서 특히 볼 판단**

| 문항 | 트레이스에서 검토할 판단 |
|---|---|
| 1, 4 | `query`가 사용자 원문 그대로인지, 최종 답의 숫자가 반환 근거에 있는지 |
| 2, 8 | `category`를 허용값 중에서 골랐는지, 인원·금액을 원문 그대로 넣었는지 |
| 3 | 빠진 금액·인원을 모델이 지어내 호출하지 않았는지 |
| 5 | 쓰기 도구 호출이 0회인지, 거절 이유와 대안 절차를 안내했는지 |
| 6 | 재시도가 1회로 끝났는지, 보류 중에 증빙 목록을 지어내지 않았는지 |
| 7 | `NO_RESULT` 뒤에 관련 없는 조항으로 답하지 않았는지, 이관 전에 동의를 받았는지 |
| 8 | `user_confirmed=true` 전에 저장하지 않았는지, `HOLD`를 모델이 아니라 서버가 판정했는지 |


===== my-service-agent/my-agent/inventory_tool.py =====
import asyncio, json, sys
from typing import Any

QUESTION = sys.argv[1] if len(sys.argv) > 1 else "부산 3번 창고의 A-17 재고를 알려 줘"

async def main():
    from langchain_core.tools import tool
    from langchain_core.messages import ToolMessage
    from langchain_ollama import ChatOllama

    @tool
    def get_inventory(sku: str, warehouse_id: str) -> dict[str, Any]:
        """승인된 창고에서 특정 상품의 현재 가용 재고를 읽기 전용으로 조회합니다.
        sku에는 상품 SKU를 넣습니다.
        warehouse_id에는 사용자가 말한 창고 이름을 바꾸거나 비슷한 코드로 고치지 말고 그대로 넣습니다.
        허용 여부는 도구가 판단합니다. 허용 창고는 SEOUL-01, BUSAN-02뿐입니다.
        WAREHOUSE_NOT_ALLOWED가 반환되면 수량을 말하지 말고, 다시 호출하지 말고,
        SEOUL-01과 BUSAN-02 중 어느 창고인지 사용자에게 물어봅니다."""
        if warehouse_id not in ("SEOUL-01", "BUSAN-02"):
            return {"error": "WAREHOUSE_NOT_ALLOWED"}
        return {"sku": sku, "warehouse_id": warehouse_id,
                "available_quantity": 7, "checked_at": "2026-08-27T01:55:00+09:00"}

    llm = ChatOllama(model="qwen3.5:2b", temperature=0, reasoning=False)
    llm_with_tools = llm.bind_tools([get_inventory])

    print("[0] 사용자 질문:", QUESTION)
    r1 = await llm_with_tools.ainvoke(QUESTION)
    print("[1] 모델의 요청:", [(tc["name"], tc["args"]) for tc in r1.tool_calls])

    result = get_inventory.invoke(r1.tool_calls[0]["args"])
    print("[2] 하네스의 실행 결과:", json.dumps(result, ensure_ascii=False))

    r2 = await llm_with_tools.ainvoke(
        [r1, ToolMessage(content=json.dumps(result, ensure_ascii=False),
                         tool_call_id=r1.tool_calls[0]["id"])])
    print("[3] 결과를 읽은 최종 답:", r2.content[:120])

asyncio.run(main())


===== my-service-agent/my-agent/tool-definition.md =====
# 도구 정의서: `get_inventory`

읽기 전용 재고 조회 도구의 계약입니다. 고객이 "부산 창고의 A-17 재고"를 물었을 때 모델이 창고와 상품을 추측하지 않도록, 여섯 항목을 먼저 고정합니다.

## 정의서

| 도구 정의서 항목 | 기록할 내용 |
|---|---|
| 이름 | `get_inventory` (동사 get + 대상 inventory) |
| 하는 일 한 문장 | 승인된 창고의 특정 SKU 가용 수량을 읽기 전용으로 조회합니다 |
| 언제 쓰고 안 쓰는지 | **쓰는 때:** 사용자가 특정 SKU의 특정 창고 재고 수량을 물을 때 씁니다. "부산 창고"처럼 허용 창고 하나로 분명히 대응될 때만 해당 코드(BUSAN-02)로 바꿔 씁니다.<br>**안 쓰는 때:** 수량 변경·입출고 요청, 창고나 SKU가 정해지지 않은 질문(먼저 묻습니다), 가격·원가·배송일 질문에는 쓰지 않습니다 |
| 인자 스키마 | `sku`: 필수, 문자열 3~32자<br>`warehouse_id`: 필수, 나열형 `SEOUL-01` 또는 `BUSAN-02`만 허용<br>그 밖의 인자는 받지 않습니다 |
| 반환 형식 | `sku`, `warehouse_id`, `available_quantity`(0 이상 정수), `checked_at`(확인 시각) 네 필드만 돌려줍니다. 원가 등 내부 데이터는 포함하지 않습니다 |
| 실패 정의와 뒤 행동 | `WAREHOUSE_NOT_ALLOWED` 허용 목록 밖 창고 → 재호출하지 않고 SEOUL-01·BUSAN-02 중 어디인지 **질문**<br>`SKU_NOT_FOUND` 없는 SKU → 비슷한 상품을 추측하지 않고 정확한 SKU를 **질문**<br>`TIMEOUT` 응답 지연·서버 오류 → 한 번 **재시도**, 다시 실패하면 **중단**하고 조회 불가를 안내(수량 추정 금지) |

- 오류 코드 이름은 "실패에 이름을 붙인다"는 원칙에 따라 정했습니다. `WAREHOUSE_NOT_ALLOWED`는 실습 2 구현(`inventory_tool.py`)이 실제로 돌려주는 이름에 맞췄고, `SKU_NOT_FOUND`·`TIMEOUT`은 정의서에만 있고 가정 구현에는 아직 없습니다.
- 이 정의서에서 "부산 창고의 A-17 재고" 질문에 가능한 호출은 `get_inventory(sku="A-17", warehouse_id="BUSAN-02")` 하나뿐입니다. 창고는 나열형이라 지어낼 수 없고, SKU가 없으면 묻게 됩니다.

## 설계 원칙

- **도구 하나는 동작 하나:** 재고 조회와 수량 변경을 한 정의서에 넣지 않습니다. 변경은 별도 도구(예: `update_stock`)의 영역입니다.
- **자유 문자열 최소화:** 창고처럼 값의 목록이 닫혀 있으면 나열형으로, 길이 제한이 있으면 범위로 적어 모델이 지어낼 자리를 줄입니다.
- **반환은 답의 근거만:** 원본 재고 데이터를 통째로 돌려주지 않고 `available_quantity`, `checked_at`처럼 답의 근거가 되는 필드로 제한합니다.
- **실패는 지금 설계:** 실패마다 뒤 행동(재시도·질문·중단)을 정해 두지 않으면 모델은 같은 호출을 되풀이합니다.

## 실행 전 채점 기준

| 채점 기준 | 통과의 이진 정의 | 확인 위치 |
|---|---|---|
| 스키마 준수 | 호출이 3~32자 `sku`와 `SEOUL-01`·`BUSAN-02` 중 하나의 `warehouse_id`만 사용했습니다 | 도구 호출 인자 |
| 호출 성공 | 유효 입력에서 4개 필드 성공 반환 또는 `WAREHOUSE_NOT_ALLOWED`·`SKU_NOT_FOUND`·`TIMEOUT` 중 하나가 남았습니다 | 도구 응답 |
| 결과 사용 가능성 | 최종 답이 `available_quantity`와 `checked_at`만 근거로 삼았습니다 | 최종 답변 |
| 실패 처리 | 오류 뒤 수량을 추정하지 않고 질문·재시도·중단 중 정해진 행동을 택했습니다 | 호출·최종 답변 |

외부 규정 검색 서버·ERP를 호출하지 않고, 호출되었다고 가정해 가상 규정 데이터로 결과를 돌려준다.

          "국내출장숙박": (100000, "item"), "해외출장숙박": (200000, "item"), "교통비": (50000, "item")}

def log(tag, text):
    print(f"[{tag}] {text}", flush=True)


async def main():
    from langchain_core.tools import tool
    from langchain_core.messages import HumanMessage, SystemMessage, ToolMessage
    from langchain_ollama import ChatOllama

    @tool
    def search_expense_policy(query: str) -> dict:
        """사내 회계 규정 문서에서 질문과 관련된 조항을 읽기 전용으로 검색합니다.
        경비 기준, 증빙 요건, 청구 절차처럼 규정 내용을 묻는 질문에 씁니다.
        특정 금액이 한도 안인지 판단할 때, 청구서 작성, 승인·이체 요청에는 쓰지 않습니다.
        query에는 사용자 질문을 바꾸지 말고 그대로 넣습니다.
        NO_RESULT가 오면 관련 없는 조항으로 답하지 말고 재무팀 이관을 제안합니다.
        TOOL_ERROR가 오면 한 번만 다시 호출하고, 또 실패하면 답을 보류합니다."""
        if os.environ.get("FAIL_SEARCH") == "1":
            return {"error": "TOOL_ERROR"}
        # 관련성 판단은 하네스가 한다: 키워드가 하나도 맞지 않으면 결과에서 뺀다
        hits = [p for p in POLICIES if any(k in query for k in p["keywords"])]
        if not hits:
            return {"error": "NO_RESULT", "checked_at": CHECKED_AT}
        return {"results": [{k: p[k] for k in ("clause_title", "condition", "effective_date", "source")}
                            for p in hits[:3]], "checked_at": CHECKED_AT}

    @tool
    def check_expense_limit(category: Category, amount: int, headcount: int = 1) -> dict:
        """경비 항목·금액·인원이 규정 한도 안인지 읽기 전용으로 계산합니다.
        사용자가 실제 금액을 말하며 한도 안인지 물을 때만 씁니다.
        금액이나 인원이 빠졌으면 호출하지 말고 사용자에게 물어봅니다. 값을 추측하지 않습니다.
        category가 목록에 없으면 비슷한 항목으로 바꾸지 말고 어떤 항목인지 물어봅니다."""
        if category not in LIMITS:
            return {"error": "INVALID_CATEGORY"}
        if amount < 1 or headcount < 1:
            return {"error": "MISSING_FIELD"}
        limit, basis = LIMITS[category]
        total = limit * headcount if basis == "person" else limit
        return {"within_limit": amount <= total, "limit_per_person": limit if basis == "person" else None,
                "total_limit": total, "over_amount": max(0, amount - total),
                "clause_title": LIMIT_CLAUSE[category], "checked_at": CHECKED_AT}

    @tool
    def draft_expense_claim(category: Category, amount: int, purpose: str,
                            receipt_attached: bool, user_confirmed: bool, headcount: int = 1) -> dict:
        """본인 명의 경비 청구서 초안을 임시 저장합니다. 제출·승인은 하지 않습니다.
        먼저 초안 내용(항목, 금액, 인원, 목적, 영수증 여부)을 사용자에게 보여주고,
        사용자가 확인했을 때만 user_confirmed=true로 호출합니다.
        최종 제출·승인, 다른 사람 명의, 영수증을 나누거나 꾸미는 요청에는 쓰지 않습니다.
        TOOL_ERROR가 오면 다시 호출하지 말고 재무팀 이관을 제안합니다."""
        if not user_confirmed:
            return {"error": "NOT_CONFIRMED"}
        limit, basis = LIMITS[category]
        total = limit * headcount if basis == "person" else limit
        reasons = []
        if amount > total:
            reasons.append(f"한도 초과 {amount - total}원")
        if not receipt_attached:
            reasons.append("영수증 없음")
        return {"claim_no": "EXP-2026-0142", "status": "HOLD" if reasons else "DRAFT",
                "hold_reason": ", ".join(reasons) or None,
                "next_step": "ERP에서 본인이 내용을 확인한 뒤 제출하면 재무팀 승인 단계로 넘어갑니다"}

    @tool
    def escalate_to_finance(reason_code: Literal["NO_POLICY", "EXCEPTION_APPROVAL", "HOLD_REVIEW",
                                                 "TOOL_FAILURE", "USER_REQUEST"], summary: str) -> dict:
        """챗봇이 처리할 수 없는 건을 재무팀 문의 큐에 넘깁니다.
        규정에 없는 항목, 한도 예외 승인, 보류 검토, 도구 오류 반복일 때 사용자가 이관에 동의한 뒤에만 씁니다.
        편법·우회 요청은 이관하지 않고 거절합니다. summary에는 개인정보를 넣지 않습니다."""
        return {"ticket_no": "FIN-2026-0087", "expected_reply": "영업일 1일 이내",
                "channel": "재무팀 슬랙 #finance-help"}

    tools = {t.name: t for t in (search_expense_policy, check_expense_limit, draft_expense_claim, escalate_to_finance)}
    system = SystemMessage(
        "너는 사내 경비 청구와 회계 규정을 안내하는 재무 어시스턴트다.\n"
        "1. 규정 내용은 search_expense_policy 결과에, 한도 판단은 check_expense_limit 결과에만 근거한다. "
        "도구 결과에 없는 금액·한도·조건은 말하지 않는다.\n"
        "2. 근거를 찾지 못했거나 규정에 없는 예외라면 확정하지 말고 '재무팀 담당자 확인 필요'라고 답한 뒤, "
        "사용자가 원하면 escalate_to_finance로 넘긴다.\n"
        "3. 청구서는 초안만 만든다. 초안 내용을 사용자에게 보여주고 확인을 받은 뒤에만 draft_expense_claim을 호출한다.\n"
        "4. 최종 제출·승인·이체, 다른 직원 정보 조회, 증빙을 나누거나 꾸미는 요청은 거절하고 정상 절차를 안내한다.\n"
        "5. 답변 끝에는 근거로 쓴 규정 조항명과 확인 시각을 적는다.")
    llm = ChatOllama(model="qwen3.5:2b", temperature=0, reasoning=False, num_predict=512)
    llm = llm.bind_tools(list(tools.values()))

    turns = sys.argv[1:] or ["팀원 4명이서 야근 식대로 총 6만 원 썼는데 한도 안이야?"]
    messages = [system]
    for user_text in turns:
        log("USER", user_text)
        messages.append(HumanMessage(user_text))
        for _ in range(6):  # 한 사용자 턴에서 도구 호출은 최대 6번
            r = await llm.ainvoke(messages)
            messages.append(r)
            if not r.tool_calls:
                log("ANSWER", r.content.strip())
                break
            for tc in r.tool_calls:
                log("CALL", f"{tc['name']} {json.dumps(tc['args'], ensure_ascii=False)}")
                try:
                    result = tools[tc["name"]].invoke(tc["args"])
                except Exception as e:  # 스키마 위반 등은 하네스가 막고 오류로 돌려준다
                    result = {"error": "SCHEMA_REJECTED", "detail": type(e).__name__}
                log("RESULT", json.dumps(result, ensure_ascii=False))
                messages.append(ToolMessage(json.dumps(result, ensure_ascii=False), tool_call_id=tc["id"]))
        else:
            log("ANSWER", "(도구 호출 6회 한도에 도달해 중단)")

asyncio.run(main())

# 도구 정의서: 사내 회계 규정·경비 정산 가이드 챗봇

임직원이 "야근 식대 한도 안이야?"라고 물었을 때 모델이 금액이나 규정을 추측하지 않도록, 도구마다 여섯 항목의 계약을 먼저 고정합니다. 실행 코드는 [`expense_agent.py`](expense_agent.py), 실행 기록은 [`traces/`](traces/)에 있습니다.

## 도구 1. 규정 검색

| 도구 정의서 항목 | 기록할 내용 |
|---|---|
| 이름 | 동사+대상: `search_expense_policy` |
| 하는 일 한 문장 | 사내 회계 규정 문서에서 질문과 관련된 조항을 읽기 전용으로 검색합니다 |
| 언제 쓰고 안 쓰는지 | 경비 기준·증빙 요건·청구 절차 질문에는 쓰고, 금액 한도 판단·청구서 작성·승인 요청에는 쓰지 않습니다 |
| 인자 스키마 | `query` 문자열 2~200자, 필수. 사용자 질문을 바꾸지 않고 그대로 넣음 |
| 반환 형식 | 규정 조항명, 적용 조건, 시행일, 출처, 확인 시각 (최대 3건) |
| 실패 정의와 뒤 행동 | `NO_RESULT`면 관련 없는 조항으로 답하지 않고 재무팀 이관 제안, `TOOL_ERROR`면 한 번 재시도 후 보류 |

## 도구 2. 한도 계산

| 도구 정의서 항목 | 기록할 내용 |
|---|---|
| 이름 | 동사+대상: `check_expense_limit` |
| 하는 일 한 문장 | 경비 항목·인원·금액이 규정 한도 안인지 읽기 전용으로 계산합니다 |
| 언제 쓰고 안 쓰는지 | 실제 금액이 있는 한도 질문에는 쓰고, 금액 없는 일반 질문·예외 승인 요청에는 쓰지 않습니다 |
| 인자 스키마 | `category`는 야근식대·회식비·접대비·국내출장숙박·해외출장숙박·교통비 중 하나, `amount` 정수(원) 1 이상, `headcount` 정수 1 이상(식대·회식비는 필수) |
| 반환 형식 | 한도 내 여부, 1인 한도, 총 한도, 초과 금액, 규정 조항명, 확인 시각 |
| 실패 정의와 뒤 행동 | `INVALID_CATEGORY`면 항목을 바꾸지 말고 질문, `MISSING_FIELD`면 빠진 값 질문, `TOOL_ERROR`면 한 번 재시도 후 보류 |

## 도구 3. 청구서 초안 저장 (쓰기)

| 도구 정의서 항목 | 기록할 내용 |
|---|---|
| 이름 | 동사+대상: `draft_expense_claim` |
| 하는 일 한 문장 | 본인 명의 경비 청구서 초안을 임시 저장합니다 (제출·승인은 하지 않음) |
| 언제 쓰고 안 쓰는지 | 사용자가 초안 내용을 확인한 뒤에만 쓰고, 확인 전·타인 명의·최종 승인 요청·증빙 조작 요청에는 쓰지 않습니다 |
| 인자 스키마 | `category`·`amount`·`headcount`는 도구 2와 같음, `purpose` 문자열 5~200자, `receipt_attached` 참/거짓, `user_confirmed` 참/거짓(거짓이면 하네스가 거부). 신청자 사번은 하네스가 로그인 정보로 채움 |
| 반환 형식 | 접수 번호, 상태(`DRAFT`·`HOLD`), 보류 사유, 다음 단계 안내 |
| 실패 정의와 뒤 행동 | `NOT_CONFIRMED`면 초안을 보여주고 확인 질문, `HOLD`(서버 판정)면 보류 사유 안내 후 이관 제안, `TOOL_ERROR`면 중복 저장 위험이 있어 재시도 없이 이관 |

## 도구 4. 재무팀 이관 (쓰기)

| 도구 정의서 항목 | 기록할 내용 |
|---|---|
| 이름 | 동사+대상: `escalate_to_finance` |
| 하는 일 한 문장 | 챗봇이 처리할 수 없는 건을 재무팀 문의 큐에 넘깁니다 |
