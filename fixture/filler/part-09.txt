

===== finance-rag-chatbot/CLAUDE.md =====
# 프로젝트 개요
K-IFRS 제1115호 수익인식 학습·문단 찾기 도우미 (브라우저 RAG 챗봇)

회계 학습자(회계 전공생, 자격시험 수험생, 회계팀 신입)가 K-IFRS 제1115호 '고객과의 계약에서 생기는 수익'의 개념을 물으면, 기준서 요약 자료에서 근거를 찾아 2~4문장으로 답하고 근거가 된 **기준서 문단 번호와 원문 링크**를 함께 보여 준다. 실제 계약의 회계처리 판단은 하지 않는다.

- 모두콘 안내 챗봇(github.com/suncreation/moducon-chatbot) 구조에서 자료와 도메인 문구만 교체한 과제 산출물이다.
- 제품 요구사항·답변 규칙·수용 기준: `PRD.md` (v2.0, 2026-10-14)
- 사용자용 설명·실험 기록: `README.md`
- 배포 주소(예정): https://rubilisa08.github.io/finance-rag-chatbot/ — 아직 열리지 않음 (아래 "현재 구현 상태" 참고)

## 목표
회계 기준 관련 질문에 근거 자료를 바탕으로 답변하는 챗봇을 만든다.

- 답변보다 **근거가 먼저** 보이게 한다: 답변 바로 아래에 인용한 문단(섹션·문단 번호·원문 링크)을 펼쳐 보여 준다.
- 자료에 없는 질문은 "제가 가진 자료에는 없습니다"로, 범위 밖 질문(주가·세무·투자·다른 기준서)은 정해진 문구로 거절한다.
- 개별 계약의 판단 질문에는 결론을 내리지 않고 관련 기준 문단만 안내하며 전문가 확인을 권한다.
- 서버 없이 브라우저와 사용자 PC의 Ollama만으로 동작한다.

## 기술 스택
| 영역 | 사용 기술 |
|---|---|
| 프런트엔드 | React 19, TypeScript 6, Vite 8 (`base: './'`), 린터 oxlint |
| 임베딩 | `onnx-community/embeddinggemma-300m-ONNX`의 `model_no_gather_q4` (q4 고정, 768차원). 브라우저는 transformers.js 4.2.0 토크나이저 + onnxruntime-web 세션 직접 생성, Node는 `scripts/node-embedder.mjs` |
| 벡터 저장소 | **DB 없음.** 정적 JSON 파일 `app/public/ifrs-docs.json`을 브라우저가 받아 메모리에서 검색 |
| 검색 | 벡터 내적(=코사인) top-10 + BM25 top-5 하이브리드 (`app/src/search-core.ts`) |
| 생성 LLM | 로컬 Ollama `qwen3.5:2b` (`http://localhost:11434/api/chat`, 스트리밍). 선택: 사용자 키로 Gemini `gemini-3.5-flash` |
| 판정 | LLM-as-a-Judge 루브릭 (`app/src/judge.ts`). 로컬은 qwen3.5:2b 자기평가 |
| 배포 | GitHub Actions → GitHub Pages (`.github/workflows/deploy.yml`, Node 20으로 빌드만) |
| 스크립트 실행 | Node 22.18 이상 (`scripts/`가 `src/*.ts`를 직접 import). 이 PC는 v24.19.0 |

## 현재 구현 상태
2026-10-14 기준, `main` 브랜치에서 확인한 내용이다.

### 동작하는 기능
- 질문 → 브라우저 임베딩 → 하이브리드 검색(근거 15개) → 프롬프트 조립(v3) → Ollama 스트리밍 답변
- 검색 단계 표시: ① 임베딩 ② 근거 검색(벡터/BM25 개수, 유사도 막대) ③ 답변 생성
- 답변 아래 `CitedParagraphs`: 답변에 적힌 ID의 문단을 펼쳐 보여 줌. ID가 없으면 검색 상위 3개, 거절·약한 근거면 숨김
- 면책 문구 `disclaimer()`: 인용 청크의 section에서 문단 번호를 뽑아 프로그램이 생성
- 출처 칩: ✓는 답변에 ID가 실제로 적힌 근거 (모델이 아니라 `citedIds()`가 확인)
- 약한 근거 경고: 1위 유사도 < 0.55면 ⚠ 배지와 프롬프트 주의 문구
- 벡터 저장소 안전장치: `ifrs-docs.meta.json`이 현재 임베딩 설정과 다르면 검색 거부
- LLM 판정 배지, 👍/👎 피드백(콘솔 기록만, 서버 전송 없음), Gemini 엔진 전환
- 터미널 도구: 검색기(`search`), 질문기(`ask`), 일괄 실험(`run-questions.mjs`, `--resume` 지원)
- `npm run build`, `npm run lint` 통과 (2026-10-14 확인)

### 자료
- 청크 30개 (`data/chunks.json`), 본문 155~330자(평균 235자)
  - 기준서 요약 26개: `IFRS-001`~`014`, `IFRS-019`~`030` (본문 일부, 부록 A 계약자산·부채, 부록 B 반품권·보증·본인 대 대리인)
  - 교육용 사내 가이드 4개: `IFRS-015`~`018` (`docs/revenue-guide.md`의 `##` 절)
- 일부러 넣지 않은 주제(근거 부족 실험용): 라이선싱, 고객의 선택권, 재매입약정, 위탁약정, 미인도청구약정 등
- 고정 질문 세트 18개 (`data/fixed-questions.json`, 2026-10-14에 4개 추가), 결과 `experiments/fixed-v3.json`. v3 기준 거절 대상 7개 중 6개 거절, 정상 질문 11개 중 잘못 거절 0, ID 인용 8/11

### 미완성·알려진 문제
- **배포 안 됨**: GitHub Pages가 꺼져 있어 Deploy 워크플로가 `configure-pages` 단계에서 실패한다(빌드 자체는 통과). 배포 주소는 404.
- **사례 판단 질문 실패**: "소프트웨어 + 1년 유지보수, 수행의무 몇 개?"에 결론("1개")을 내리고 엉뚱한 청크(IFRS-026)를 인용함
- **근거 부족 질문 실패**: "라이선스 수익은 언제 인식해?"에 자료에 없는 내용을 지어냄
- **5단계 개요 질문**: 5단계 중 이행 단계 한 문장만 답함 (개요 청크 없음)
- **개념 비교 질문**: "계약부채와 수익은 어떻게 다른가요?"에 계약자산 vs 계약부채를 비교함 (여러 청크를 잇지 못함)
- **출처 표기 흔들림**: 일부 답변이 ID 대신 "(문단 22)"처럼 문단 번호만 적음 → ✓가 안 붙고 "관련될 수 있는 문단"으로 표시됨
- **일상어 질문 검색 약함**: "대금을 먼저 받으면 바로 매출로 인식하나요?"에서 정답 청크 IFRS-014가 근거 15개 안에 안 들어옴 (청크가 기준서 용어로만 쓰여 있음)
- 판정이 같은 2B 모델의 자기평가라 관대함 (README 실험 0)
- 속도: GPU가 없는 이 PC에서 답변 1~3분(평균 약 179초), 판정은 몇 분 더

## 실행 방법
모든 명령은 `app` 폴더에서 실행한다.

```bash
npm install
npm run dev                                          # http://localhost:5173 (CORS 설정 불필요)
npm run build                                        # tsc + vite build → app/dist
npm run lint                                         # oxlint
npm run embed                                        # data/chunks.json → public/ifrs-docs.json + meta 재생성
node scripts/embed-docs.mjs --verify public/ifrs-docs.json 3   # 저장된 벡터 재현 확인 (1.000000이어야 함)
npm run search -- "계약부채가 뭐야?" "내일 날씨 어때?"            # 검색만 (기본 top-3, --k 15로 앱과 같은 15개)
npm run ask -- "계약부채가 뭐야?" --show-prompt                 # 모델 입력만 출력 (Ollama 불필요)
npm run ask -- "계약부채가 뭐야?"                               # 답변 + 근거 목록 (--judge로 판정까지)
node scripts/run-questions.mjs --name fixed-v3 --format v3 [--questions 파일] [--judge] [--resume]
```

사전 준비
- Ollama 설치 후 `ollama pull qwen3.5:2b`
- 첫 실행 때 임베딩 모델(약 200MB)을 받는다. Node는 `~/.cache/embeddinggemma-onnx`, 브라우저는 Cache Storage(`moducon-embed-v1`)
- 배포 주소에서 쓰려면 `OLLAMA_ORIGINS=https://*.github.io` 설정 후 Ollama 재시작 (OS별 방법은 README "사용 조건")

## 작업 규칙

### 답변 규칙 (제품)
- 회계 기준 관련 답변에는 근거 출처를 표시한다: 근거가 된 청크 ID를 `[IFRS-xxx]`처럼 문장 끝에 적고, 화면은 그 청크의 문단 번호와 원문 URL을 보여 준다.
- 근거를 확인할 수 없는 내용은 확정적으로 답변하지 않는다. 자료에 없으면 "제가 가진 자료에는 없습니다"라고 답한다.
- 개별 계약의 판단은 결론 없이 관련 기준만 안내하고 전문가(작성자·감사인) 확인을 권한다.
- 범위 밖(주가, 세무, 투자, 다른 기준서, 실시간 데이터)은 정해진 문구로 거절한다. 상세 기준은 PRD 5장.
- 근거 표시와 면책 문구는 모델에 맡기지 않고 프로그램이 만든다(`citedIds()`, `disclaimer()`).

### 바꾸지 않는 것 (과제 조건)
결과 차이를 자료 차이로 읽기 위해 유지한다. 이 중 하나를 바꾸면 **실험**이다.
- 벡터 저장소 스키마 `[{ id, text, url, section, vector }]`
- 검색 순서: 벡터 top-10 + BM25 top-5 (`rankHybrid()`, 모두콘 `retrieve()` 로직 그대로)
- 프롬프트의 근거·출처 규칙, "근거 약함" 기준(1위 < 0.55), 판정 로직(`judge.ts`)

### 실험 규칙
- 한 번에 변수 하나만 바꾸고, 전후를 같은 질문으로 비교해 README "실험 결과"에 기록한다.
- 실패한 답도 지우지 않는다. 결과 원문은 `experiments/`에 남긴다.
- 프롬프트 형식을 바꾸면 `PROMPT_FORMAT`을 새 버전으로 두고 이전 버전은 비교 재현용으로 남긴다(v1·v2·v4 보존, v4는 실험 5에서 기각).

### 임베딩 계약
- 정의는 `app/src/embed-format.ts`에만 둔다. 브라우저(`rag.ts`)와 Node(`node-embedder.mjs` → `embed-docs.mjs`, `search.mjs`)가 모두 이 파일을 쓴다.
- 벡터: `last_hidden_state` → mean pooling → L2 정규화, 768차원 (내적 = 코사인).
- 입력 형식 `INPUT_FORMAT = "embeddinggemma-official-v1"`
  - 문서: `"title: " + section + " | text: " + text`
  - 질문: `"task: search result | query: " + question`
- q4/q8 기본 파일은 브라우저 WASM에서 `GatherBlockQuantized` 미지원이라 쓰지 않는다.
- 모델이나 입력 형식을 바꾸면 `INPUT_FORMAT` 값을 올리고 `npm run embed`로 저장소를 다시 만든다.

### 검색 계약
- 순위 계산은 `rankHybrid()` 한 곳에만 둔다. 터미널 결과 = 앱 결과 (동점끼리는 WASM/CPU 소수점 차이로 순서가 바뀔 수 있음).
- BM25가 5개를 못 채우면 벡터 11위부터 보충해 항상 k개. 앱은 k=15 고정, CLI는 기본 3.
- `WEAK_THRESHOLD`는 `search-core.ts`에서만 정의하고 프롬프트·화면·CLI가 import한다. 근거: 실험 1에서 무관한 질문 0.47~0.50, 관련 질문 0.70 이상. "법인세 절세"(0.581)처럼 기준 위인 범위 밖 질문은 프롬프트 규칙으로 거절한다.
- `search.mjs`는 직접 실행될 때만 CLI를 돈다. 다른 파일은 `search()`를 import해 재사용한다.

### 생성 계약
- 시스템 메시지와 프롬프트 조립은 `app/src/prompt.ts`에만 둔다. 앱과 터미널(`ask.mjs`, `run-questions.mjs`)이 같은 코드를 쓴다. 시스템 메시지 내용은 제품 결정이라 PRD 5장과 맞춰 레포 소유자가 정한다.
- 사용자 메시지 순서: ① 자료 소개 ② 근거 원칙(1위 < 0.55면 "주의: …") ③ 출처 규칙 ④ KST 현재 시각 ⑤ `[자료]` + `[IFRS-xxx] (section) text` 줄들 ⑥ `[질문]` ⑦ 출처 규칙 한 번 더
- v3 출처 규칙은 예시 ID로 **검색 1위 ID**를 쓴다. 고정 예시 ID를 쓰면 모델이 그 ID를 베껴 넘기지 않은 청크를 인용한다(실험 3).
- Ollama 호출: `{ stream: true, think: false, options: { temperature: 0 } }`, NDJSON을 `TextDecoder({ stream: true })`로 읽는다. 연결 확인은 실제 호출할 때만 한다.

### 데이터 규칙
- 청크 원본은 `data/chunks.json`. 벡터 저장소는 여기서 만들고 직접 고치지 않는다.
- 청크 하나에 중심 사실 하나, `text` 120자 이상, `id`는 `IFRS-001`부터 빈 번호 없이.
- 기준서 청크: `text`는 기준서 문장을 옮기지 않고 **직접 요약**한다. 원문에 없는 해석·예시·수치를 넣지 않는다. `text` 끝과 `section`에 문단 번호, `url`은 한국회계기준원 회계기준열람서비스(`https://db.kasb.or.kr/s/1115/...`)의 해당 목차 페이지.
- 사내 가이드 청크: `section`은 `교육용 사내 가이드 - 제목`, `url`은 `https://github.com/rubilisa08/finance-rag-chatbot/blob/main/docs/revenue-guide.md#제목`(공백은 하이픈). 사내 절차만 쓰고 회계기준 내용은 쓰지 않는다.

### 저작권
- 기준서 원문의 저작권은 IFRS 재단에 있다. 공개 레포이므로 **원문 발췌본은 레포에 넣지 않는다.** 원문은 레포 밖 PC 폴더에만 두고 요약 검증에만 쓴다.
- 열람서비스(db.kasb.or.kr)는 `robots.txt`가 `Disallow: /`이므로 스크립트로 수집하지 않는다. 원문은 사람이 브라우저에서 읽고 복사한다.

# PRD — K-IFRS 제1115호 수익인식 학습·문단 찾기 도우미

버전 v2.0 · 2026-10-14 · 모두콘 안내 챗봇 구조를 재무·회계 도메인으로 교체한 과제 산출물
(v1.0의 "안내 챗봇"에서 "학습·문단 찾기 도우미"로 제품 정의를 좁힘 — 11장 결정 기록 참고)

## 1. 사용자와 문제
- **사용자**: K-IFRS 제1115호를 공부하는 **회계 학습자** (회계 전공생, 회계 자격시험 수험생, 수익인식을 처음 배우는 회계팀 신입)
- **문제**: 기준서는 본문·적용지침·적용사례를 합쳐 수백 문단이라, "계약부채가 뭐지?", "본인과 대리인은 어떻게 구분하지?" 같은 개념을 공부할 때 **해당 문단을 찾는 데 시간이 오래 걸린다.** 요약 자료나 검색 결과는 출처가 없거나 원문과 다를 때가 있다.
- **사용자가 끝내 할 수 있어야 하는 일**: 짧은 요약을 읽고, 근거가 된 **기준서 문단을 바로 열어 원문으로 공부**한다.
- **이 챗봇이 아닌 것**: 실제 계약의 회계처리를 판단해 주는 도구. 수익인식은 매출·이익에 직접 영향을 주는 민감한 영역이라, 판단은 사람(회계 담당자·감사인)이 하고 챗봇은 공부와 원문 찾기를 돕는다.

## 2. 목표
한 문장 목표: 회계 학습자가 수익인식 기준을 물으면, 2~4문장으로 짧게 요약하고 근거가 된 기준서 문단을 원문 링크와 함께 보여 준다. 개별 계약의 판단은 하지 않는다.

- K-IFRS 제1115호의 핵심 원칙, 수익인식 5단계, 주요 주제(계약변경, 진행률, 변동대가, 금융요소, 할인액 배분, 계약원가, 반품권, 보증, 본인 대 대리인), 계약자산·계약부채 용어를 다룬다.
- **답변보다 근거가 먼저 보이게** 한다: 답변 바로 아래에 답변이 인용한 문단(섹션·문단 번호·원문 링크)을 펼친 상태로 보여 준다. 답변이 ID를 빠뜨리면 검색 상위 문단을 "관련될 수 있는 문단"으로 보여 준다.
- 검색 단계(유사도·근거 조각)와 출처를 드러내는 RAG 답변을 제공한다. 모든 근거에는 기준서 **문단 번호**와 원문 URL을 붙여, 원문의 해당 위치를 찾을 수 있게 한다.
- 답변을 스트리밍으로 표시한다.
- 답변마다 판정 배지(LLM-as-a-Judge)와 좋아요·싫어요 피드백을 기록할 수 있게 한다. 로컬 판정은 같은 qwen3.5:2b 모델의 자기평가라 독립 평가가 아니며, 교육용 참고 신호로 읽는다.

## 3. 비목표
- 로그인, 사용자 계정 관리, 개인별 학습 기록 저장
- 실시간 주가 조회, 개별 기업의 공시 원본 검색, 외부 금융 DB 연동
- 세무 대리, 회계 감사 의견 표명, 투자 자문 등 법적·실무적 의사결정을 대신하는 기능
- **개별 계약의 회계처리 판단과 결론** (학습용이므로 관련 기준 문단 안내까지만 한다 — 5장 참고)
- 실무 판례·금융감독원 질의회신 검색 (자료에 넣지 않았다)
- K-IFRS 제1115호 외 기준서(리스, 금융상품 등)와 일반기업회계기준의 안내
- 다국어 지원, 모바일 최적화 레이아웃, 판정·피드백의 서버 수집

## 4. 자료 범위와 출처
- **원문**: 한국회계기준원(KASB) 회계기준열람서비스의 K-IFRS 제1115호 — https://db.kasb.or.kr/s/1115
- **사용 범위**: 본문 문단 1~2, 9~10, 18~19, 22, 27, 31~32, 35, 38~41, 44~45, 47, 51, 53, 56~57, 60~61, 63, 73~74, 77, 81~82, 91~95, 부록 A(용어의 정의), 적용지침 B20~B21, B28~B30, B34~B36 → 기준서 청크 26개 (`IFRS-001`~`014`, `IFRS-019`~`030`)
- **교육용 사내 가이드**: [`docs/revenue-guide.md`](docs/revenue-guide.md) — 계약 검토 체크리스트, 판단이 어려운 계약 처리, 증빙과 기록 보관, 실무 용어와 기준서 용어 → 청크 4개 (`IFRS-015`~`IFRS-018`)
  - 실제 회사 규정이 아닌 일반화된 사내 절차(검토자, 문의 순서, 마감·증빙)만 담는다. 회계기준의 내용은 쓰지 않는다.
  - `section`은 "교육용 사내 가이드 - 제목", `url`은 GitHub의 파일 주소 + 제목 앵커다. 배포 화면에서도 출처 링크가 열리게 하기 위해서다.
- **청크 작성 원칙**
  - 청크 하나에 중심 사실 하나, 120자 이상
  - `text`는 기준서 문장을 옮기지 않고 **직접 요약**한다. 원문에 없는 해석·예시·수치는 넣지 않는다.
  - `text` 끝과 `section`에 문단 번호를 적는다. `url`은 그 문단이 있는 열람서비스 목차 페이지다.
- **저작권**: 기준서 원문의 저작권은 IFRS 재단에 있다([저작권 고지](https://db.kasb.or.kr/s/1115/copyright)). 공개 레포에는 직접 쓴 요약만 두고, 원문 발췌본은 레포 밖에 보관한다.
- **갱신 주체와 링크 책임**: 레포 소유자가 기준서 개정 여부와 출처 링크가 열리는지를 확인한다. 청크를 바꾸면 `data/chunks.json`을 고치고 `app/scripts/embed-docs.mjs`로 벡터스토어를 다시 만든다.
- **일부러 넣지 않은 1115호 주제**: 라이선싱, 고객의 선택권, 재매입약정, 위탁약정, 미인도청구약정 등. 이 주제들은 "근거 부족" 질문으로 실험에 쓴다.

## 6. 아키텍처
모두콘 안내 챗봇의 구조를 그대로 쓰고, 데이터와 도메인 문구만 교체했다. 검색 순서와 프롬프트의 출처·거부 규칙은 바꾸지 않았다.
```
GitHub Pages (정적) — Actions로 main push마다 app/dist 배포
 └─ React + Vite SPA (백엔드 없음)
     ① 질의 임베딩  — embeddinggemma-300m (model_no_gather_q4, 768차원), 브라우저에서 실행
     ② 근거 검색    — 하이브리드: 벡터 유사도 top-10 + BM25 top-5 (총 15)
     ③ 답변 생성    — 로컬 ollama qwen3.5:2b 스트리밍 (선택: Gemini API)
     ④ 판정         — LLM-as-a-Judge: 근거 충실성·환각 통제·출처 표시 + refusal 플래그
     ⑤ 피드백       — 👍👎 토글 (세션 내 콘솔 기록)
```
- 벡터스토어 `app/public/ifrs-docs.json` — 30청크(기준서 요약 26 + 사내 가이드 4), 각 `{id, text, url, section, vector[768]}`
- 벡터는 `app/scripts/embed-docs.mjs`로 만든다. 질문 임베딩(`rag.ts`의 `embed()`)과 같은 모델 파일·같은 계산(mean pooling, L2 정규화)을 써서 질문과 문서가 같은 벡터 공간에 있다. 브라우저 계산 결과와 Node 계산 결과가 일치하는 것을 확인했다.
- **임베딩 계약**은 `app/src/embed-format.ts` 한 곳에서 정의하고 브라우저와 Node가 함께 쓴다. 입력 형식은 EmbeddingGemma 공식 형식이다 — 문서 `title: 섹션 | text: 본문`, 질문 `task: search result | query: 질문`. 자세한 내용은 `CLAUDE.md`.
- 안전장치: 벡터스토어 옆 `ifrs-docs.meta.json`에 모델·입력 형식을 기록하고, 현재 설정과 다르면 검색을 거부한다. 벡터스토어 스키마는 바꾸지 않는다.
- **생성 계약**: 시스템 메시지와 프롬프트 조립은 `app/src/prompt.ts` 한 곳에서 정의하고 앱과 터미널 질문기(`app/scripts/ask.mjs`)가 함께 쓴다. 출처 표시 형식은 v3(자료 줄 `[ID] (섹션) 본문`, 출처 예시 ID = 검색 1위), 답변 `temperature` 0. 근거 목록의 ✓는 프로그램이 답변에서 ID를 찾아 붙인다.
- **검색 계약**: 하이브리드 순위 계산과 약한 근거 기준(`WEAK_THRESHOLD = 0.55`)은 `app/src/search-core.ts` 한 곳에서 정의하고, 앱과 터미널 검색기(`app/scripts/search.mjs`)가 함께 쓴다. 로직은 모두콘 구조에서 위치만 옮겼다.

## 7. 화면 상태
- 답변 스트리밍 중: 검색된 근거 박스(ID·섹션·검색 방식·점수)를 표시
- 답변 완료: 출처 칩(기본 접힘) → 누르면 근거 조각과 "기준서 원문 보기" 링크

# K-IFRS 1115 수익인식 학습 도우미

K-IFRS 제1115호 '고객과의 계약에서 생기는 수익'을 공부하다 궁금한 개념이 생기면, 그 답이 기준서 **어느 문단에 있는지** 찾아 주는 챗봇입니다.

- 질문하면 짧게 요약하고, 근거가 된 기준서 문단을 원문 링크와 함께 보여 줍니다.
- 공부를 돕는 도구라 실제 계약의 회계처리는 판단하지 않습니다.
- 서버 없이 브라우저와 내 PC의 Ollama(`qwen3.5:2b`)만으로 동작합니다.

배포 주소: https://rubilisa08.github.io/finance-rag-chatbot/ (GitHub Pages 설정 전이라 아직 열리지 않습니다. 지금은 [로컬에서 실행하기](#로컬에서-실행하기)로 써 주세요) · 제품 요구사항: [PRD.md](PRD.md)
[모두콘 안내 챗봇](https://github.com/suncreation/moducon-chatbot)의 구조를 바탕으로 만들었습니다.

## K-IFRS 제1115호란?

회사가 물건이나 서비스를 팔았을 때 **매출(수익)을 언제, 얼마로 장부에 적을지** 정한 회계 기준입니다. 정식 이름은 '고객과의 계약에서 생기는 수익'입니다.

핵심 원칙은 "돈을 받은 때"가 아니라 **"고객에게 약속한 것을 넘겨준 때"**, 그 대가로 받을 것으로 기대하는 금액만큼 수익을 인식한다는 것입니다(문단 2).

이 원칙은 다섯 단계로 적용합니다.

| 단계 | 하는 일 |
|---|---|
| 1. 계약 식별 | 고객과 계약이 실제로 성립했는지 확인한다 |
| 2. 수행의무 식별 | 고객에게 해 주기로 한 약속을 하나하나 나눈다 |
| 3. 거래가격 산정 | 받을 대가가 얼마인지 정한다 |
| 4. 거래가격 배분 | 약속이 여러 개면 가격을 약속마다 나눠 붙인다 |
| 5. 수익 인식 | 약속을 지킬 때(또는 지켜 가는 만큼) 수익으로 적는다 |

## 다루는 질문과 다루지 않는 질문

| 다루는 것 | 다루지 않는 것 |
|---|---|
| 제1115호의 핵심 원칙 | 주가 전망, 세무(절세·신고), 투자 자문 |
| 수익인식 5단계 (계약 식별 → 수행의무 식별 → 거래가격 산정 → 배분 → 수행의무 이행) | 리스, 금융상품 등 다른 기준서 |
| 계약자산·계약부채 용어, 계약변경, 진행률, 변동대가 제약, 유의적인 금융요소, 할인액 배분, 계약원가, 반품권, 보증, 본인 대 대리인, 교육용 사내 검토 절차 | 개별 계약의 회계처리 **판단과 결론** (관련 기준 문단만 안내하고 전문가 확인을 권함) |
| | 실무 판례·금융감독원 질의회신 (자료에 없음) |

자료에 없는 질문에는 "제가 가진 자료에는 없습니다"라고 답하도록 했습니다. 다만 2B 모델이라 완벽하지 않아서, 실제로 지어낸 사례도 실험 결과에 그대로 적었습니다. 상황별 처리 기준은 [PRD.md 5장](PRD.md#5-답변-규칙)에 있습니다.

**화면에서 보이는 것**: 답변 바로 아래에 **답변이 인용한 기준서 문단**(문단 번호, 원문 링크)이 펼쳐져 나옵니다. 요약보다 원문이 정확하니 링크를 열어 원문으로 확인하세요. 답변이 근거 ID를 빠뜨리면 검색 상위 문단을 "관련될 수 있는 문단"으로 보여 주고, 범위 밖 질문을 거절했을 때는 보여 주지 않습니다. 그 아래에는 프로그램이 자동으로 만든 안내 문구가 붙습니다.

> 본 답변은 K-IFRS 제1115호 기준서 요약(문단 B20~B21)에 기초한 학습용 참고 자료입니다. 저작권 때문에 기준서 원문 대신 직접 쓴 요약을 쓰므로 정확한 표현은 원문 링크에서 확인하고, 실제 회계처리는 작성자와 감사인의 판단이 필요합니다.

문단 번호는 답변이 인용한 근거에서 프로그램이 뽑아 넣습니다. 모델에게 맡기면 빠뜨리거나 틀린 번호를 쓸 수 있어서입니다.

## 기준서 원문을 그대로 쓰지 않은 이유 (저작권)

**짧게 말하면**: 기준서 문장은 저작권이 있는 글이고 이 레포는 누구나 볼 수 있는 공개 레포라서, 원문을 옮기지 않고 **직접 요약해서** 썼습니다. 원문은 복사해 두는 대신 **공식 사이트의 해당 문단으로 안내**합니다.

**1. 기준서는 누구의 글인가**
K-IFRS는 국제회계기준(IFRS)을 한국어로 옮긴 것이고, 원 저작권은 **IFRS 재단**에 있습니다. 한국회계기준원 회계기준열람서비스의 [저작권 고지](https://db.kasb.or.kr/s/1115/copyright)에는 재단의 서면 승인 없이 기준서의 전부나 일부를 번역·복제·재배포하는 것을 원칙적으로 금지한다는 내용이 있습니다. 한국 안에서 쓰는 경우에 대해 일부 권리를 주장하지 않는다는 예외 문구도 있지만, 전 세계에 공개되는 GitHub 레포가 그 예외에 들어가는지는 분명하지 않습니다.

**2. RAG에서는 왜 특히 문제가 되나**
RAG 챗봇은 자료를 청크 파일(`data/chunks.json`, `app/public/ifrs-docs.json`)에 담아 레포에 올리고, 배포한 페이지가 방문자의 브라우저로 이 파일을 내려보냅니다. 청크에 원문을 그대로 넣으면 **기준서 일부를 레포와 배포 페이지를 통해 그대로 다시 배포하는 셈**이 됩니다.

**3. 그래서 이렇게 했습니다**
- 청크의 `text`는 해당 문단을 **내 말로 요약**했습니다. 수행의무, 개별 판매가격처럼 뜻이 정해진 회계 용어는 정확성을 위해 그대로 썼습니다.
- 요약과 원문이 얼마나 겹치는지 프로그램으로 쟀습니다. 가장 길게 겹치는 구간이 청크마다 **11~33자**(용어나 짧은 구절 수준)이고, 문장을 통째로 옮긴 곳은 없습니다.
- 모든 기준서 청크에 **문단 번호**와 열람서비스의 **해당 목차 URL**을 붙였습니다. 원문을 레포에 복사하는 대신 공식 사이트의 원문을 읽도록 안내하는 방식입니다.
- 요약을 검증하려고 모은 원문 발췌본은 **레포 밖의 내 PC에만** 두었고, 레포에는 올리지 않았습니다.
- 화면의 답변 아래 안내 문구와 이 README에 이 사실을 적었습니다.

**4. 쓰는 사람이 알아 둘 점**
- 답변은 "기준서를 요약한 자료"를 다시 요약한 것이라, **표현이 원문과 다를 수 있고 요약 과정의 오류가 있을 수 있습니다.** 공부할 때는 근거 문단의 원문 링크를 꼭 열어 보세요.
- 과제, 시험 답안, 실무 문서에 인용할 때는 이 챗봇의 문장이 아니라 **원문 문장**을 쓰세요.

**5. 이 방식의 대가**
원문을 그대로 넣었다면 표현은 더 정확했을 것입니다. 요약하면서 원문에 없는 해석이 섞일 위험이 생기는데, 이것은 원문과 한 문장씩 대조하는 검토로 관리했습니다. 이 판단은 법률 자문을 받은 것이 아니라 공개 레포에서 가장 무난한 방식을 고른 것입니다.

4. **브라우저**: Chrome 또는 Edge를 권장합니다. "로컬 네트워크 접근"을 물으면 허용합니다.

## 설계 결정 요약

- **"안내 챗봇"이 아니라 "학습·문단 찾기 도우미"**: 처음에는 회계팀 실무자에게 기준을 안내하는 챗봇으로 시작했지만, 실험에서 가장 크게 틀린 것이 실제 계약 판단 질문과 자료에 없는 주제 질문이었습니다. 2B 모델과 요약 자료로 실무 판단을 돕는 것은 위험하다고 보고, 사용자를 학습자로 좁혔습니다(PRD v2.0). 시스템 메시지만 바꾸는 방법은 효과가 없어서(실험 5 기각), 근거 문단을 답변 아래에 펼쳐 보여 주고 면책 문구를 프로그램이 붙이는 방식으로 구현했습니다.
- **도메인을 제1115호 하나로 좁힘**: 회계기준 전체를 다루면 청크 몇 개로는 근거가 부족해집니다. 범위를 좁혀 "자료 안 / 자료 밖"의 경계를 분명히 했습니다.
- **원문 출처와 문단 번호**: 모든 청크는 한국회계기준원 회계기준열람서비스의 해당 목차 페이지 URL과 기준서 문단 번호를 가집니다. 출처 칩 → "기준서 원문 보기"로 원문의 해당 위치를 찾을 수 있습니다.
- **청크는 직접 요약**: 공개 레포에 기준서 문장을 옮기지 않기 위해 `text`는 문단을 직접 요약했습니다. 원문에 없는 해석·예시·수치는 넣지 않았습니다.
- **사례 판단 질문은 거절하지 않음**: 신입이 실제로 많이 물을 질문이라, 결론은 내리지 않되 판단에 필요한 기준은 근거와 함께 안내합니다.
- **임베딩 공간 통일**: 질문 임베딩(`app/src/rag.ts`의 `embed()`)과 같은 모델 파일·같은 계산으로 청크 벡터를 만들었습니다(`app/scripts/embed-docs.mjs`). 같은 문장을 Node와 브라우저에서 임베딩해 결과가 일치하는 것을 확인했습니다.
- **임베딩 계약을 한 곳에서 정의**: 모델과 입력 형식(문서 `title: 섹션 | text: 본문`, 질문 `task: search result | query: 질문`)은 `app/src/embed-format.ts`에만 있고 브라우저와 Node가 함께 씁니다. 벡터스토어 옆 `ifrs-docs.meta.json`의 설정이 현재 설정과 다르면 검색을 거부합니다. 입력 형식은 아래 실험 1의 측정값으로 정했습니다.
- **바꾸지 않은 것과 바꾼 것**: 검색 순서, 근거 원칙, 판정 로직은 모두콘 구조 그대로입니다. 임베딩 입력 형식과 출처 표시 형식은 실험으로 근거를 남기고 바꿨습니다. 아래 [과제 조건과 달라진 점](#과제-조건과-달라진-점) 참고.
- **근거 표시는 프로그램이 확인**: 2B 모델은 ID를 빼먹거나 다르게 적기도 하므로, 출처 칩의 ✓(답변에 ID가 실제로 적힌 근거)는 모델이 아니라 프로그램이 답변을 보고 붙입니다.

### 터미널 질문기와 실험 실행
앱과 같은 검색·프롬프트·Ollama 호출을 터미널에서 씁니다.
```bash
cd app
npm run ask -- "계약부채가 뭐야?" --show-prompt     # 모델에 들어가는 system/user 메시지만 출력 (Ollama 불필요)
```

`run-questions.mjs`는 질문마다 답변 원문과 측정값(cited, 머리 베낌, 가짜 ID, 시간)을 `experiments/<실험이름>.json`에 남깁니다.

### 실험 1 — 임베딩 입력 형식
- 바꾼 변수: 임베딩 입력 형식 하나 (나머지 조건·질문·순서는 그대로)
  - 이전: 접두어 없이 원문 그대로
  - 이후: EmbeddingGemma 공식 형식 — 문서 `title: 섹션 | text: 본문`, 질문 `task: search result | query: 질문`
- 조건: 청크 17개(기준서 요약 14 + 사내 가이드 3), `model_no_gather_q4`, 질문 13개, 각 질문의 검색 1위 점수
- 측정: Node에서 두 형식으로 각각 임베딩해 비교. 바꾼 뒤 브라우저 앱에서도 같은 점수가 나오는 것을 확인했습니다(계약부채 0.772, 주가 0.497, IFRS-016 0.720).

| 내일 삼성전자 주가 오를까요? | 0.579 (기준 0.55 위) | **0.497 (기준 아래 → 근거 약함 경고)** |

- 결정: **채택.** 무관한 질문의 점수가 내려가 관련 질문과의 간격이 약 3배로 넓어졌고, 사내 가이드 질문의 정답 청크가 1위로 올라왔습니다.
- 추가 관찰(`npm run search -- "수익인식 5단계가 뭐야?" --k 15`): 1~5단계 청크(IFRS-002·004·006·009·011)가 모두 벡터 상위 10개 안에 들어, 여러 청크를 잇는 질문도 검색 단계에서는 근거가 모델에 전달됩니다.
- 남은 문제: "법인세 절세" 질문은 "수익", "인식" 같은 회계 단어가 겹쳐 아직 0.55보다 높습니다. 이 질문의 거절은 프롬프트의 범위 밖 규칙에 달려 있으므로, 생성 단계 실험에서 `refusal` 결과를 확인합니다.

### 생각해 볼 것
1. **단어가 겹치지 않아도 찾을 수 있나?** 임베딩은 단어가 아니라 뜻을 비교하므로 가능은 합니다. 2번에서 정답이 "계약부채"라는 단어 없이도 3위 안에 들었습니다. 하지만 우리 자료에서는 **1위까지는 못 올라왔고**, 5번 "선수금"처럼 실무 용어와 기준서 용어가 다르면 거의 못 찾았습니다(17위). 실무 용어(선수금)와 기준서 용어(계약부채)를 잇는 문장이 청크에 있으면 나아질 수 있습니다.
2. **8·9번도 1위 청크는 항상 나옵니다.** 검색은 "가장 가까운 것"을 고를 뿐 "답이 있는지"는 모릅니다. 그래서 점수 기준(0.55)이 필요하고, 실제로 무관한 질문(0.42~0.49)은 걸러졌습니다.
3. **7·10·11번은 기준을 통과해 버립니다.** "매출", "회계처리", "법인세"처럼 회계와 가까운 단어가 있으면 점수가 올라갑니다. **검색 점수만으로는 "실시간 매출은 자료에 없다", "리스는 범위 밖이다"를 걸러 낼 수 없습니다.** 그래서 시스템 프롬프트에 범위 밖 규칙(주가·세무 거절, 다른 기준서 안내)을 넣었습니다.
4. **단어 하나에 끌려 엉뚱한 청크가 올라오기도 합니다.** 10번은 "회계처리"에 사내 가이드가, 7번은 "매출"에 변동대가 청크가 끌려왔습니다. 그래서 모델에게 "근거에 있는 내용만" 쓰라고 해야 합니다.

→ 이것이 "검색만으로는 부족하고 생성 단계(규칙을 아는 LLM)가 필요한 이유"입니다.

### 내가 쓴 문서 추가 전후 비교 (사내 가이드 3개)
같은 질문을 사내 가이드 청크 3개(IFRS-015~017)를 빼고(14개) / 넣고(17개) 검색했습니다.

| 질문 | 추가 전 1위 | 추가 후 1위 |
|---|---|---|
| 판단이 안 서는 계약은 누구한테 물어봐? | IFRS-003 계약의 정의 **0.670** (엉뚱함) | **IFRS-016 판단이 어려운 계약 처리 0.720** |
| 검수 확인서는 어디에 보관해? | IFRS-003 계약의 정의 **0.553** (엉뚱함, 기준을 겨우 넘음) | **IFRS-017 증빙과 기록 보관 0.696** |
| 계약서 받으면 회계팀은 뭘 확인해? | IFRS-002 계약 식별 기준 0.672 (비슷하지만 다른 내용) | **IFRS-015 계약 검토 체크리스트 0.766** |
| 계약부채가 뭐야? | IFRS-014 0.772 | IFRS-014 0.772 (그대로). 단, **3위가 IFRS-004 → IFRS-015로 바뀜** |
| 수행의무는 어떻게 식별해? | IFRS-004 0.703 | 그대로 (1~3위 모두 같음) |

1. **추가 전에도 ⚠ 경고가 뜨지 않았습니다.** 점수는 0.553~0.672로 기준을 넘었지만 내용은 엉뚱했습니다. 특히 "계약서 받으면 회계팀은 뭘 확인해?"에 기준서의 계약 식별 기준이 나온 것은 **비슷해 보이지만 다른 상황**입니다(사내 절차 질문인데 회계기준이 답으로 쓰일 수 있음). 점수 기준만으로는 맞는 자료인지 보장할 수 없습니다.
2. 자료를 넣자 **정확한 청크가 높은 점수로 1위**가 됐습니다. RAG의 답변 품질은 **자료가 있느냐**에 가장 크게 좌우됩니다.
3. 상관없어 보이는 "계약부채" 질문도 **3위가 바뀌었습니다.** 자료를 바꿀 때마다 이 관찰 질문들을 다시 돌려 봐야 합니다.

### 실험 2 — 사내 가이드에 "실무 용어와 기준서 용어" 절 추가
- 바꾼 변수: 자료 하나 — `docs/revenue-guide.md`에 `## 실무 용어와 기준서 용어` 절을 추가해 청크 IFRS-018로 넣음 (17 → 18청크). 임베딩·검색·프롬프트는 그대로.
- 이유: 위 관찰 5번에서 "선수금"처럼 실무 용어로 물으면 기준서 용어(계약부채) 청크를 거의 못 찾았습니다(17위). 기준서 청크에 "선수금"을 넣으면 원문에 없는 내용이 되므로, **사내 관행**(이 실무 용어는 이 기준으로 검토한다)으로 가이드에 적었습니다.

| 질문 | 추가 전 1위 | 추가 후 1위 | IFRS-018 순위 |
|---|---|---|---|
| 선수금은 어떻게 처리해? | IFRS-009 거래가격 배분 0.584 (엉뚱함) | **IFRS-018 0.612** | 1위 |
| 매출할인이나 리베이트는 어떻게 반영해? | IFRS-007 변동대가가 생기는 경우 0.687 | **IFRS-018 0.709** (2위 IFRS-007) | 1위 |
| 미청구 금액은 뭐로 봐야 해? | IFRS-006 거래가격 산정 0.640 (엉뚱함) | IFRS-006 0.640 그대로 | **2위** (0.620) |
| 세트로 묶어서 팔면 수행의무는 어떻게 봐? | IFRS-004 수행의무 식별 0.629 | 그대로 | 5위 |
| 고객한테 돈을 먼저 받았는데 아직 물건을 안 줬으면 그건 뭐야? | IFRS-011 0.687 (정답 IFRS-014는 3위) | 그대로 | 6위 |

회귀 확인 (원래 질문 10개의 1위):
- 정상 질문 5개(계약부채, 변동대가, 수행의무, 판단 보류, 검수 확인서)는 1위와 점수가 **모두 그대로**였습니다.
- 무관 질문(날씨, 김치찌개)도 그대로 ⚠ 표시됩니다.
- **부작용 1건**: "우리 회사 이번 달 매출이 얼마야?"(도메인 밖)의 1위가 IFRS-008(0.613) → IFRS-018(0.617)로 바뀌었습니다. 새 절의 "매출"이라는 단어에 끌린 것입니다. 원래도 기준(0.55) 위였어서 걸러지지 않는 것은 같고, 거절은 프롬프트 규칙에 맡깁니다.

- 결정: **채택.** 실무 용어 질문 2개에서 용어 대응 청크가 1위, 1개에서 2위로 올라왔고 정상 질문은 나빠지지 않았습니다.
- 한계: 용어 대응 청크는 "어느 기준으로 검토하라"까지만 알려 줍니다. 정의(계약부채 IFRS-014)는 여전히 상위 3위 밖이라, 모델이 두 청크를 이어 답해야 합니다. 앱은 근거를 15개 넘기므로(18개 중) IFRS-014도 모델에 전달되기는 합니다.
- 관찰: 청크가 18개인데 앱은 근거를 15개 넘기므로, 지금 규모에서는 **검색이 "무엇을 빼느냐"보다 "어떤 순서로 보여 주느냐"**에 가깝습니다. 자료가 늘면 이 차이가 커집니다.

### 실험 3 — 출처 표시 형식 (프롬프트)
- 바꾼 변수: 프롬프트의 출처 표시 형식 하나 (자료 줄 모양 + 출처 규칙 문장). 검색·자료(18청크)·질문·순서는 그대로.
- 먼저 바꾼 설정: 답변 호출에 `temperature: 0`을 넣었습니다(전에는 판정에만 있었음). 같은 질문에 같은 답이 나와야 형식 차이를 비교할 수 있기 때문입니다. 세 형식 모두 이 조건에서 돌렸습니다.
- 질문 5개 (`data/exp3-questions.json`), 근거 15개, qwen3.5:2b. 원문 답변: `experiments/exp3-v1.json`, `exp3-v2.json`, `exp3-v3.json`
- 측정은 프로그램이 합니다(`app/scripts/run-questions.mjs`): 넘긴 근거의 ID가 답에 있나(cited), 자료 줄 머리 `[IFRS-xxx | 섹션]`을 베꼈나, 넘기지 않은 ID를 지어냈나

| 형식 | 자료 줄 | 출처 규칙 | cited | 머리 베낌 | 가짜 ID | 평균 |
|---|---|---|---|---|---|---|
| v1 (모두콘 그대로) | `[IFRS-016 \| 섹션] 본문` | "근거가 된 조각의 [ID]를 답 안에서 표시" | 4/5 | **3/5** | 0/5 | 191초 |

- 좋아진 것: "변동대가는 어떻게 추정해?"에서 추정 방법(문단 53)과 추정치의 제약(문단 56~57)을 **이어서** 답했습니다. 고정 질문에서 두 청크를 연결한 첫 사례입니다. "계약부채"에 ID 인용이 생겼습니다.
- 나빠진 것: "수익인식 5단계가 뭐야?"에 답한 뒤 끝에 "본 챗봇은 K-IFRS 제1115호 회계기준 범위 내의 질문에만 답변할 수 있습니다"를 **엉뚱하게 덧붙였습니다**(잘못된 거절 1건). "판단이 안 서는 계약" 답은 68자로 뭉뚱그려졌고, 사내 가이드를 "기준서 원문"이라고 불렀습니다. "2~4문장으로 짧게" 지시는 길이를 줄이지 못했습니다.
- 결정: **기각, v3 유지.** 2B 모델은 시스템 메시지로 역할과 답변 길이를 바꿔도 잘 따르지 않았고, 가장 큰 실패(사례 판단 결론, 라이선스 환각)도 그대로였습니다.
- 그래서 제품 정의 변경(PRD v2.0 "학습·문단 찾기 도우미")은 **모델에 맡기지 않고 프로그램이 확실하게 하는 부분**으로 구현했습니다: 답변 아래 근거 문단 블록(펼친 상태), 프로그램이 문단 번호를 넣는 면책 문구, 화면·문서의 범위 안내. v4는 비교 재현을 위해 코드에 남겨 둡니다.

### 참고: BM25 하이브리드
튜토리얼의 선택 심화(벡터 + BM25 하이브리드)는 모두콘 구조에 이미 들어 있습니다. 앱과 `npm run search -- … --k 15`는 벡터 상위 10개 + BM25 상위 5개를 씁니다. 기본 top-3 관찰에는 벡터 결과만 보입니다.

## 왜 K-IFRS 제1115호인가

이 도메인을 고른 이유는 세 가지입니다. 이유마다 실제 측정 결과와 한계를 함께 적습니다.

**1. 5단계 모형이라는 분명한 구조**
- 기대: 기준서가 "계약 식별 → 수행의무 식별 → 거래가격 산정 → 배분 → 인식"으로 짜여 있어, 청크를 단계별로 나누고 질문이 몇 단계에 해당하는지 찾기 쉽다.
- 결과: 청크 `section`을 `수익인식 5단계 - 3단계 거래가격 산정 (문단 47)`처럼 단계와 문단으로 구조화했고, **검색은 이 구조대로 동작**했습니다. 단계별 직접 질문은 정답 청크가 1위였고(실험 1·4: 직접 질문 7/7, 새 주제 질문 10/12), "5단계가 뭐야?"에는 1~5단계 청크가 모두 상위 10위 안에 들었습니다.
- 한계: **답변 단계에서는 구조가 다 살지 못했습니다.** 2B 모델이 여러 청크를 잇지 못해 "5단계" 질문에 한 단계만 답했고, 근거 부족 질문에서 환각이 1건 나왔습니다(고정 질문 실험). 구조 덕분에 검색은 정확하지만, 환각이 적다고 말하기에는 아직 근거가 부족합니다. 또 기준서 본문에는 5단계를 한곳에 나열한 문단이 없어서 개요 청크를 기준서 문단으로 만들 수 없었습니다.

**2. 도메인 밖 질문의 경계가 분명함**
- 기대: 1115호는 "수익을 언제, 얼마로 인식하는가"만 다루므로 주가·투자·세무 질문을 깔끔하게 거절할 수 있다.
- 결과: 시스템 메시지에 "본 챗봇은 K-IFRS 제1115호 회계기준 범위 내의 질문에만 답변할 수 있습니다"를 정해 두었고, 고정 질문 실험에서 **도메인 밖 질문 5개(주가, 주식 매수, 법인세, 개인 세무, 이번 달 매출)를 모두 거절**했습니다. 주가·주식 질문은 정해진 문구 한 줄로 답했습니다. 동시에 **정상 질문 7개는 하나도 잘못 거절하지 않았습니다.**
- 한계: 검색 점수만으로는 경계가 갈리지 않습니다. "법인세", "매출", "리스"처럼 회계 단어가 섞인 질문은 점수가 0.58~0.63으로 기준(0.55)을 넘어서, 거절은 모델이 규칙을 지키는 데 달려 있습니다. 그리고 가장 어려운 건 도메인 밖이 아니라 **"1115호 안이지만 자료에 없는" 질문**이었습니다(라이선스 질문에서 환각).

**3. 공식 원문이 있어 근거를 확인할 수 있음**
- 기대: 기준서는 공식 원문과 문단 번호가 있어 "기준서 조항을 근거로 답한다"고 설명하기 좋다.
- 결과: 모든 기준서 청크는 한국회계기준원 회계기준열람서비스의 실제로 열리는 URL과 문단 번호를 가지고, 출처 칩 → "기준서 원문 보기"로 해당 위치를 찾을 수 있습니다. 청크는 원문과 대조해 만들었고(가장 긴 겹침 11~33자), 저작권 고지를 화면과 README에 넣었습니다.
- 한계: 공개 레포라 원문 대신 **직접 쓴 요약**이어서, 요약의 정확성은 사람이 원문과 대조해 확인해야 합니다. 사내 가이드 청크 4개는 교육용 가상 문서라 "기준서 조항"이 아니라 사내 절차 근거로 구분해 읽어야 합니다. 처음 정한 불편(비용 처리 기준)과 달리 도메인은 수익인식이라, 사용자 문제를 "수익인식 기준을 원문에서 찾지 못하는 불편"으로 다시 정리했습니다.

## 과제 조건과 달라진 점

과제는 "스키마와 검색·프롬프트 파이프라인을 바꾸지 말고, 검색 순서와 답변 프롬프트의 출처·거부 규칙은 그대로 두라"고 합니다. 결과 차이를 자료 차이로 읽기 위해서입니다. 아래는 그대로 둔 것과, 실험 근거를 갖고 바꾼 것입니다.

| 항목 | 상태 | 근거 |
|---|---|---|
| 벡터스토어 스키마 `{id, text, url, section, vector}` | **그대로** | 설정 기록은 별도 파일(`ifrs-docs.meta.json`)로 분리 |
| 검색 순서 (벡터 top-10 + BM25 top-5) | **그대로** | 코드 위치만 `search-core.ts`로 옮김 (로직 동일, 앱·터미널 결과 일치 확인) |
| 근거 약함 기준 0.55와 보수 지시 문구 | **그대로** | 한 곳(`WEAK_THRESHOLD`)에서 정의하도록 정리만 함 |
| 거부 규칙 ("자료에 없으면 없다고 말한다") | **그대로** | 도메인 밖·다른 기준서·사례 판단 처리는 PRD에서 정한 대로 시스템 메시지에 **추가** |
| 임베딩 입력 형식 | **변경** | 실험 1 — 관련·무관 질문의 점수 간격 0.042 → 0.115 |
| 프롬프트 출처 표시 형식 | **변경** | 실험 3 — v1은 머리 베낌 3/5와 잘못된 거절, v3은 위험한 실패 0건 |
| 답변 `temperature` | **추가 (0)** | 실험 비교를 위해 같은 질문에 같은 답이 나오도록 |

바꾼 항목은 모두 한 번에 변수 하나만 바꾸고, 바꾸기 전 형식(v1 등)을 코드에 남겨 다시 비교할 수 있게 했습니다.

## 출처와 저작권

이 챗봇의 청크는 한국회계기준원 회계기준열람서비스에 공개된 K-IFRS 제1115호 '고객과의 계약에서 생기는 수익'을 참고해 **직접 요약**한 것입니다. 기준서 원문의 저작권은 IFRS 재단에 있으며, 정확한 내용은 각 출처 링크의 원문을 확인하세요 ([저작권 고지](https://db.kasb.or.kr/s/1115/copyright)).

왜 원문 대신 요약을 썼는지는 [기준서 원문을 그대로 쓰지 않은 이유 (저작권)](#기준서-원문을-그대로-쓰지-않은-이유-저작권)에 자세히 적었습니다. 사내 가이드(`docs/revenue-guide.md`)는 이 프로젝트를 위해 직접 쓴 교육용 가상 문서입니다.

이 챗봇은 공부를 돕는 교육용 도구이며, 회계 자문이나 실제 회계처리 판단을 대신하지 않습니다.

## 한계와 확장 방향
- **자료 범위**: 기준서 본문·적용지침 중 26개 문단 묶음만 요약했습니다. 라이선싱, 고객의 선택권, 재매입약정 등은 일부러 넣지 않았고(근거 부족 질문 실험용), 적용사례(IE)와 **금융감독원 질의회신·실무 해석 사례는 넣지 않았습니다.** 실무 질문에 강한 도구가 되려면 이런 자료를 이용 조건을 확인한 뒤 추가해야 합니다.
- **모델 크기**: 로컬 2B 모델이라 여러 청크를 잇는 답과 자료에 없는 주제의 거절이 약합니다(고정 질문 실험의 라이선스 환각, "5단계" 질문의 불완전한 답). 같은 구조에서 Gemini 엔진을 고르면 더 큰 모델로 비교해 볼 수 있습니다.
- **5단계 뼈대 고정**: 5단계 개요를 시스템 메시지에 고정해 두면 "5단계가 뭐야?" 같은 질문이 나아질 수 있습니다. 다음 실험 후보로 남겨 두었습니다.

// 터미널 질문기 — 앱과 같은 검색·프롬프트·Ollama 호출로 답변을 스트리밍하고 근거 출처를 보여 준다
// 검색: search.mjs(search-core.ts), 프롬프트: src/prompt.ts, LLM·판정: src/ollama.ts
//
// 사용법 (app 폴더에서):
//   node scripts/ask.mjs "질문" [--show-prompt] [--k 15] [--format v1|v2|v3] [--judge]
//   --show-prompt  LLM에 보내는 system/user 메시지를 출력하고 끝낸다 (Ollama 없이 동작)
//   --k            모델에 넘길 근거 수 (기본 15 = 앱과 같음)
//   --format       프롬프트 형식 (기본 = src/prompt.ts의 PROMPT_FORMAT)
//   --judge        답변 뒤에 LLM-as-a-Judge 판정도 돌린다 (앱과 같은 qwen 자기평가, 몇 분 더 걸림)

import { pathToFileURL } from "node:url";
import { search, WEAK_THRESHOLD } from "./search.mjs";
import { buildPrompt, systemMessage, citedIds, PROMPT_FORMAT, PROMPT_FORMATS } from "../src/prompt.ts";
import { chatStream, pingOllama, judgeWithOllama } from "../src/ollama.ts";

const MODEL = "qwen3.5:2b";

/** LLM에 보낼 메시지 — 앱(App.tsx)과 같은 구성 */
export function buildMessages(question, hits, format = PROMPT_FORMAT) {
  return [
    { role: "system", content: systemMessage(format) },
    { role: "user", content: buildPrompt(question, hits, format) },
  ];
}

/** 질문 하나 → 검색 → 생성 (실험 스크립트에서 재사용) */
export async function answer(question, { k = 15, format = PROMPT_FORMAT, onToken = () => {} } = {}) {
  const hits = await search(question, k);
  const messages = buildMessages(question, hits, format);
  const t0 = Date.now();
  const text = await chatStream(messages, onToken, MODEL);
  return { question, format, hits, text, cited: [...citedIds(text, hits)], ms: Date.now() - t0 };
}

/** Ollama가 켜져 있는지 — 꺼져 있으면 안내하고 false */
export async function checkOllama() {
  if (await pingOllama()) return true;
  console.error("✗ Ollama에 연결할 수 없습니다. Ollama가 실행 중인지 확인하세요.");
  console.error("  확인: ollama list   (목록이 나오면 실행 중, 오류면 Ollama 앱을 실행)");
  console.error(`  모델: ollama pull ${MODEL}`);
  return false;
}

function printSources(hits, cited) {
  console.log(`\n📚 근거 (모델에 넘긴 ${hits.length}개 중 답변에 인용 ${cited.size}개, ✓ = 답변에 ID가 적힘)`);
  for (const h of hits) {
    const mark = cited.has(h.chunk.id) ? "✓" : " ";
    console.log(`  ${mark} ${h.chunk.id}  ${h.score.toFixed(3)}  [${h.chunk.section}]`);
    if (cited.has(h.chunk.id)) console.log(`      ${h.chunk.url}`);
  }
}

async function main(argv) {
  let question = null, showPrompt = false, judge = false, k = 15, format = PROMPT_FORMAT;
  for (let i = 0; i < argv.length; i++) {
    if (argv[i] === "--show-prompt") showPrompt = true;
    else if (argv[i] === "--judge") judge = true;
    else if (argv[i] === "--k") k = Number(argv[++i]);
    else if (argv[i] === "--format") format = argv[++i];
    else question = argv[i];
  }
  if (!question || !(k > 0) || !PROMPT_FORMATS.includes(format)) {
    console.error('사용법: node scripts/ask.mjs "질문" [--show-prompt] [--k 15] [--format v1|v2|v3] [--judge]');
    process.exit(1);
  }

  if (showPrompt) {
    const hits = await search(question, k);
    const [sys, user] = buildMessages(question, hits, format);
    console.log(`(프롬프트 형식 ${format}, 근거 ${hits.length}개, 1위 ${hits[0].score.toFixed(3)} / 약한 근거 기준 ${WEAK_THRESHOLD})`);
    console.log(`\n[system]\n${sys.content}\n\n[user]\n${user.content}`);
    return;
  }

  if (!(await checkOllama())) process.exit(1);
  console.log(`Q: ${question}\n`);
  const r = await answer(question, { k, format, onToken: (t) => process.stdout.write(t) });
  console.log(`\n\n(생성 ${(r.ms / 1000).toFixed(1)}초, 프롬프트 형식 ${format})`);
  printSources(r.hits, new Set(r.cited));

  if (judge) {
    console.log("\n④ 판정 중… (qwen3.5:2b 자기평가)");
    const src = r.hits.map((h) => `[${h.chunk.id}] ${h.chunk.text}`).join("\n"); // 앱과 같은 근거 문자열

    console.log(`grounded=${v.grounded} cited=${v.cited} refusal=${v.refusal} — “${v.comment}”`);
  }
}

// 청크 → 벡터스토어 생성 스크립트 (Node)
// 임베딩은 node-embedder.mjs(= src/rag.ts embed()와 같은 계산), 모델·입력 형식은 src/embed-format.ts.
//
// 사용법 (app 폴더에서):
//   node scripts/embed-docs.mjs <청크.json> <출력.json>     청크에 vector를 붙여 저장 + <출력>.meta.json 기록
//   node scripts/embed-docs.mjs --verify <벡터스토어.json> [개수]
//                                                           저장된 벡터와 다시 만든 벡터의 코사인 비교

import { readFile, writeFile } from "node:fs/promises";
import { MODEL_ID, MODEL_FILE, DIM, INPUT_FORMAT } from "../src/embed-format.ts";
import { embedDocument } from "./node-embedder.mjs";

const cosine = (a, b) => a.reduce((s, v, i) => s + v * b[i], 0);

async function verify(storePath, n) {
  const docs = JSON.parse(await readFile(storePath, "utf8"));
  for (const d of docs.slice(0, n)) {
    const v = await embedDocument(d);
    console.log(`${d.id}  저장된 벡터와 코사인 유사도 = ${cosine(v, d.vector).toFixed(6)}`);
  }
}

/** 임베딩 전에 청크 검사 — 필드 누락·중복 id는 중단, 120자 미만은 경고 */
function checkChunks(chunks) {
  const seen = new Set();
  for (const [i, c] of chunks.entries()) {
    const missing = ["id", "text", "url", "section"].filter((k) => !c[k]);
    if (missing.length) throw new Error(`${i + 1}번째 청크(${c.id ?? "id 없음"})에 필드 누락: ${missing.join(", ")}`);
    if (seen.has(c.id)) throw new Error(`중복 id: ${c.id}`);
    seen.add(c.id);
    if (c.text.length < 120) console.warn(`⚠ ${c.id}: text가 ${c.text.length}자입니다 (120자 이상 권장)`);
  }
}

async function build(inPath, outPath) {
  const chunks = JSON.parse(await readFile(inPath, "utf8"));
  checkChunks(chunks);
  const out = [];
  for (const { id, text, url, section } of chunks) {
    const vector = await embedDocument({ section, text });
    out.push({ id, text, url, section, vector });
    console.log(`✓ ${id} (${section})`);
  }
  const bad = out.filter((c) => c.vector.length !== DIM);
  if (bad.length) throw new Error(`${DIM}차원이 아닌 벡터: ${bad.map((c) => `${c.id}(${c.vector.length})`).join(", ")}`);
  // 학습용: 벡터가 어떻게 생겼는지, 정규화됐는지(노름 1.0) 확인
  const first = out[0].vector;
  const norm = Math.sqrt(first.reduce((s, v) => s + v * v, 0));
  console.log(`첫 벡터 앞 5개: [${first.slice(0, 5).map((v) => v.toFixed(4)).join(", ")}]  노름: ${norm.toFixed(4)}`);
  await writeFile(outPath, JSON.stringify(out));
  // 안전장치: 어떤 설정으로 만들었는지 옆에 기록 — rag.ts·search.mjs가 현재 설정과 다르면 검색을 거부한다
  const metaPath = outPath.replace(/\.json$/, ".meta.json");
  const meta = { model: MODEL_ID, modelFile: MODEL_FILE, dim: DIM, inputFormat: INPUT_FORMAT, count: out.length, createdAt: new Date().toISOString() };
  await writeFile(metaPath, JSON.stringify(meta, null, 2) + "\n");
  console.log(`저장: ${outPath} — ${out.length}청크 × ${DIM}차원 (설정 기록: ${metaPath})`);
}

const args = process.argv.slice(2);
try {
  if (args[0] === "--verify") await verify(args[1], Number(args[2] ?? 3));
  else if (args.length === 2) await build(args[0], args[1]);
  else {
    console.error("사용법: node scripts/embed-docs.mjs <청크.json> <출력.json> | --verify <벡터스토어.json> [개수]");
    process.exit(1);
  }
} catch (e) {
  console.error(`✗ 중단: ${e.message}`);
  process.exit(1);
}

// Node용 임베딩 파이프라인 — embed-docs.mjs(문서)와 search.mjs(질문)가 함께 쓴다
// src/rag.ts의 embed()와 같은 계산:
//   embeddinggemma-300m model_no_gather_q4.onnx + 같은 토크나이저 → mean pooling → L2 정규화 (768차원)
//   모델·입력 형식은 src/embed-format.ts 한 곳에서 가져온다
// 파이프라인(ORT 세션 + 토크나이저)은 처음 한 번만 만들어 재사용한다.
// 모델 파일은 처음 한 번만 내려받아 ~/.cache/embeddinggemma-onnx 에 보관한다 (레포에 넣지 않음).

import { mkdir, stat, rename } from "node:fs/promises";
import { createWriteStream } from "node:fs";
import { Readable } from "node:stream";
import { pipeline } from "node:stream/promises";
import { homedir } from "node:os";
import { join } from "node:path";
import * as ort from "onnxruntime-node";
import { AutoTokenizer } from "@huggingface/transformers";
import { MODEL_ID, MODEL_FILE, documentInput, queryInput } from "../src/embed-format.ts";

const HF_ONNX = `https://huggingface.co/${MODEL_ID}/resolve/main/onnx`;
const FILES = [`${MODEL_FILE}.onnx`, `${MODEL_FILE}.onnx_data`];
const CACHE_DIR = join(homedir(), ".cache", "embeddinggemma-onnx");

async function download(file) {
  const dest = join(CACHE_DIR, file);
  try {
    await stat(dest);
    return dest;
  } catch {
    // 캐시에 없으면 내려받는다
  }
  console.log(`내려받는 중: ${file}`);
  const res = await fetch(`${HF_ONNX}/${file}`);
  if (!res.ok || !res.body) throw new Error(`모델 파일 내려받기 실패 (${res.status}): ${file}`);
  const tmp = `${dest}.part`;
  await pipeline(Readable.fromWeb(res.body), createWriteStream(tmp));
  await rename(tmp, dest);
  return dest;
}

let ready = null;

/** ORT 세션 + 토크나이저 — 한 번만 만든다 */
function ensureReady() {
  if (!ready) {
    ready = (async () => {
      console.log("임베딩 모델 불러오는 중…(첫 실행은 다운로드, 약 200MB)");
      await mkdir(CACHE_DIR, { recursive: true });
      const paths = [];
      for (const f of FILES) paths.push(await download(f));
      // .onnx_data는 같은 폴더에 있으면 onnxruntime-node가 자동으로 읽는다
      const session = await ort.InferenceSession.create(paths[0], { executionProviders: ["cpu"] });
      const tokenizer = await AutoTokenizer.from_pretrained(MODEL_ID);
      return { session, tokenizer };
    })();
  }
  return ready;
}

/** 입력 문자열 → 768차원 벡터 (src/rag.ts embed()와 같은 계산). 입력 형식은 붙이지 않는다. */
export async function embed(text) {
  const { session, tokenizer } = await ensureReady();
  const enc = await tokenizer(text);
  const toOrt = (t) => new ort.Tensor("int64", BigInt64Array.from(t.data, (x) => BigInt(x)), t.dims);
  const out = await session.run({ input_ids: toOrt(enc.input_ids), attention_mask: toOrt(enc.attention_mask) });
  const hs = out.last_hidden_state;
  const [, seq, hid] = hs.dims;
  const am = enc.attention_mask.data;
  const acc = new Float64Array(hid);
  let cnt = 0;
  for (let s = 0; s < seq; s++) {
    const w = Number(am[s]);
    cnt += w;
    if (!w) continue;
    for (let h = 0; h < hid; h++) acc[h] += hs.data[s * hid + h];
  }
  let norm = 0;
  for (let h = 0; h < hid; h++) {
    acc[h] /= cnt;
    norm += acc[h] * acc[h];
  }
  norm = Math.sqrt(norm);
  return Array.from(acc, (v) => v / norm);
}

/** 문서 청크 → 벡터 (문서용 입력 형식) */
export const embedDocument = (chunk) => embed(documentInput(chunk));

/** 질문 → 벡터 (질문용 입력 형식) */
export const embedQuery = (question) => embed(queryInput(question));

// 실험용 일괄 실행 — 질문 목록을 같은 조건으로 돌려 답변 원문과 측정값을 파일로 남긴다
// 실패한 답도 지우지 않고 그대로 기록한다 (README 실험 기록의 근거).
//
// 사용법 (app 폴더에서):
//   node scripts/run-questions.mjs --name exp3-v1 --format v1 [--questions ../data/fixed-questions.json] [--judge] [--resume]
//   --resume  같은 이름의 결과 파일이 있으면 끝난 질문은 건너뛰고 이어서 실행
//   → ../experiments/<name>.json

import { readFile, writeFile, mkdir } from "node:fs/promises";
import { fileURLToPath } from "node:url";
import { answer, checkOllama } from "./ask.mjs";
import { judgeWithOllama } from "../src/ollama.ts";
import { PROMPT_FORMAT, PROMPT_FORMATS, refusalSignals } from "../src/prompt.ts";

const OUT_DIR = fileURLToPath(new URL("../../experiments/", import.meta.url));
const DEFAULT_QUESTIONS = fileURLToPath(new URL("../../data/fixed-questions.json", import.meta.url));

/** 답변에서 출처 표시 모양을 측정 */
function measure(r) {
  const allIds = [...r.text.matchAll(/IFRS-\d{3}/g)].map((m) => m[0]);
  const given = new Set(r.hits.map((h) => h.chunk.id));
  return {
    cited: r.cited.length > 0,                                  // 넘긴 근거의 ID가 하나라도 적혔나
    citedIds: r.cited,
    unknownIds: [...new Set(allIds.filter((id) => !given.has(id)))], // 넘기지 않은 ID를 지어냈나
    literalIdPlaceholder: r.text.includes("[ID]"),               // "[ID]"라는 글자를 그대로 썼나
    copiedHeader: /\[IFRS-\d{3}\s*\|/.test(r.text),              // "[IFRS-014 | 섹션]" 머리를 베꼈나
    ...refusalSignals(r.text),                                   // 거절 여부 (src/prompt.ts — 화면과 같은 기준)
    chars: r.text.length,
  };
}

async function main(argv) {
  let name = null, format = PROMPT_FORMAT, qPath = DEFAULT_QUESTIONS, judge = false, k = 15, resume = false;
  for (let i = 0; i < argv.length; i++) {
    if (argv[i] === "--name") name = argv[++i];
    else if (argv[i] === "--format") format = argv[++i];
    else if (argv[i] === "--questions") qPath = argv[++i];
    else if (argv[i] === "--judge") judge = true;
    else if (argv[i] === "--k") k = Number(argv[++i]);
    else if (argv[i] === "--resume") resume = true;
  }
  if (!name || !PROMPT_FORMATS.includes(format)) {
    console.error("사용법: node scripts/run-questions.mjs --name <실험이름> --format v1|v2|v3 [--questions 파일] [--judge] [--k 15] [--resume]");
    process.exit(1);
  }
  if (!(await checkOllama())) process.exit(1);
  const questions = JSON.parse(await readFile(qPath, "utf8"));
  await mkdir(OUT_DIR, { recursive: true });
  const outPath = `${OUT_DIR}${name}.json`;
  let results = [];
  if (resume) {
    // 중간에 멈춘 실험을 이어서 — 조건이 같을 때만 (temperature 0이라 같은 질문은 같은 답)
    try {
      const prev = JSON.parse(await readFile(outPath, "utf8"));
      if (prev.format !== format || prev.k !== k) throw new Error(`이전 실행과 조건이 다릅니다 (format ${prev.format}/${format}, k ${prev.k}/${k})`);
      results = prev.results.filter((row) => questions.some((q) => q.question === row.question));
      console.log(`이어서 실행: 완료 ${results.length}개 건너뜀`);
    } catch (e) {
      if (e.code !== "ENOENT") throw e;
    }
  }
  for (const [i, q] of questions.entries()) {
    if (results.some((row) => row.question === q.question)) continue;
    const r = await answer(q.question, { k, format });
    const row = {
      type: q.type, question: q.question, expect: q.expect ?? null, expectRefusal: q.expectRefusal ?? null,
      top1: `${r.hits[0].chunk.id} ${r.hits[0].score.toFixed(3)}`,
      ...measure(r), seconds: +(r.ms / 1000).toFixed(1), answer: r.text,
    };
    if (judge) {
      const src = r.hits.map((h) => `[${h.chunk.id}] ${h.chunk.text}`).join("\n");
      try {
        const v = await judgeWithOllama(q.question, src, r.text);
        row.judge = { score: v.score, grounded: v.grounded, noHalluc: v.noHalluc, cited: v.cited, refusal: v.refusal, comment: v.comment };
      } catch (e) {
        row.judge = { error: e.message };
      }
    }
    results.push(row);
    results.sort((a, b) => questions.findIndex((x) => x.question === a.question) - questions.findIndex((x) => x.question === b.question));
    // 중간에 멈춰도 그때까지의 결과가 남도록 매 질문마다 저장
    await writeFile(outPath, JSON.stringify({ name, format, k, model: "qwen3.5:2b", temperature: 0, runAt: new Date().toISOString(), results }, null, 2) + "\n");
    const refusalOk = row.expectRefusal === null ? "" : row.refused === row.expectRefusal ? " ✓" : " ✗";
    console.log(`[${i + 1}/${questions.length}] ${q.question} — ${row.seconds}초, cited=${row.cited} (${row.citedIds.join(",") || "-"}), 거절=${row.refused}${refusalOk}, 머리베낌=${row.copiedHeader}${row.judge ? `, 판정 ${row.judge.score ?? "실패"}` : ""}`);
  }
  console.log(`저장: ${outPath}`);
}

try {
  await main(process.argv.slice(2));
} catch (e) {
  console.error(`✗ 중단: ${e.message}`);
  process.exit(1);
}

// 터미널 검색기 — 질문을 넣으면 앱과 같은 하이브리드 검색 결과를 점수와 함께 보여 준다
// 임베딩: node-embedder.mjs (질문용 입력 형식), 순위 계산: src/search-core.ts (앱과 같은 코드)
//
// 사용법 (app 폴더에서):
//   node scripts/search.mjs "질문1" ["질문2" …] [--k 3]
//   --k 15 로 실행하면 앱이 모델에 넘기는 근거 15개(벡터 10 + BM25 5)를 그대로 볼 수 있다.

import { readFile } from "node:fs/promises";
import { fileURLToPath, pathToFileURL } from "node:url";
import { metaMismatch } from "../src/embed-format.ts";
import { rankHybrid, isWeak, WEAK_THRESHOLD } from "../src/search-core.ts";
import { embedQuery } from "./node-embedder.mjs";

const STORE = fileURLToPath(new URL("../public/ifrs-docs.json", import.meta.url));
const META = fileURLToPath(new URL("../public/ifrs-docs.meta.json", import.meta.url));

let docs = null;

/** 벡터스토어 읽기 — 메타가 현재 임베딩 계약과 다르면 거부 */
async function loadStore() {
  if (docs) return docs;
  let meta;
  try {
    meta = JSON.parse(await readFile(META, "utf8"));
  } catch {
    throw new Error("벡터스토어 메타 파일이 없습니다 — node scripts/embed-docs.mjs ../data/chunks.json public/ifrs-docs.json 을 다시 실행하세요");
  }
  const why = metaMismatch(meta);
  if (why) throw new Error(`벡터스토어와 현재 임베딩 설정이 다릅니다: ${why} — embed-docs.mjs를 다시 실행하세요`);
  docs = JSON.parse(await readFile(STORE, "utf8"));
  return docs;
}

/** 질문 하나 검색 — 앱의 retrieve()와 같은 순위 (2단계에서 재사용) */
export async function search(question, k = 3) {
  const [store, q] = await Promise.all([loadStore(), embedQuery(question)]);
  return rankHybrid(store, q, question, k);
}

export { WEAK_THRESHOLD };

const bar = (score) => {
  const n = Math.max(0, Math.min(20, Math.round(score * 20)));
  return "█".repeat(n) + "░".repeat(20 - n);
};

function print(question, hits) {
  const warn = isWeak(hits) ? `  ⚠ 관련 자료가 약함(<${WEAK_THRESHOLD})` : "";
  console.log(`\nQ: ${question}${warn}`);
  hits.forEach((h, i) => {
    const how = h.method === "bm25" ? "BM25" : "벡터";
    console.log(`  ${i + 1}. ${h.chunk.id}  ${h.score.toFixed(3)}  ${bar(h.score)}  ${how}  [${h.chunk.section}]`);
    console.log(`     ${h.chunk.text.slice(0, 60)}…`);
    console.log(`     출처: ${h.chunk.url}`);
  });
}

async function main(argv) {
  const questions = [];
  let k = 3;
  for (let i = 0; i < argv.length; i++) {
    if (argv[i] === "--k") k = Number(argv[++i]);
    else questions.push(argv[i]);
  }
  if (!questions.length || !(k > 0)) {
    console.error('사용법: node scripts/search.mjs "질문1" ["질문2" …] [--k 3]');
    process.exit(1);
  }
  for (const q of questions) print(q, await search(q, k));
}

// 다른 파일이 search()를 import할 때는 CLI를 돌리지 않는다 (node -e 등으로 argv[1]이 없을 때도 안전하게)
if (process.argv[1] && import.meta.url === pathToFileURL(process.argv[1]).href) {
  try {
    await main(process.argv.slice(2));
  } catch (e) {
    console.error(`✗ 중단: ${e.message}`);
    process.exit(1);
  }
}
